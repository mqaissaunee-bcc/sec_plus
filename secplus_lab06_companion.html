Vulnerability Checks with OpenVAS

A vulnerability scanner is how an organization finds its weak spots before an attacker does. You'll point OpenVAS at a deliberately broken host, run a full scan, and read the report the way an analyst does — by severity, and with an eye for what's real.

⏱ ~45 min (scan runs in background) 📶 Difficulty: Beginner→Intermediate 🧰 Tools: OpenVAS (GVM) · Docker 🎯 Target: Metasploitable2 (127.0.0.1) 📘 Maps to: Module 9 — Vulnerability Management, Monitoring, and Enterprise Controls

📋 Overview

What a vulnerability scan is, and the honest limits of one.

OpenVAS checks a target against a huge database of known flaws and returns a ranked list of what it found. The lab runs two containers on Kali — OpenVAS itself and a famously broken target, Metasploitable2 — and because Docker forwards the target's ports to the local machine, you scan 127.0.0.1. The real skill isn't clicking "scan"; it's reading the report: sorting by severity, understanding CVSS scores, and knowing that a scanner reports potential problems, some of which are false positives.

[THE ONE IDEA] A scan finds; it never fixes. The output is the start of the vulnerability-management cycle (identify → prioritize → remediate → re-scan), not the end of the job.

🧭 The walkthrough

Stand up the scanner and the target, then scan and read.

Phase 1 · Start the services

Scanner and target in containers

kali@kali$ sudo docker run --rm -d -p 443:443 --name openvas mikesplain/openvas kali@kali$ sudo docker run --rm -ditP icarossio/metasploitable2 kali@kali$ sudo docker images # verify both images exist

OpenVAS publishes its web dashboard on port 443; Metasploitable2 is the victim. Because Docker maps the target's ports onto the host, OpenVAS will scan 127.0.0.1 and reach the target through those forwarded ports. Give the scanner a few minutes to finish loading its feeds before logging in.

Phase 2 · Define the target

Tell OpenVAS what to look at

Log into the OpenVAS dashboard, then Configuration → Targets and add a new target named metasploitable at 127.0.0.1. A target is just a host (or range) plus the ports and scan settings to use against it.

📸Screenshot for your report: the configured target (metasploitable, 127.0.0.1).
Phase 3 · Run the scan

Create a task and launch it

Under Scans → Tasks, add a task named metasploitable scan bound to that target, then start it. The scan runs in the background and can take several minutes — a full-and-fast scan sends thousands of checks.

📸Screenshot for your report: the running (or completed) scan task.
Phase 4 · Read the report

Where the learning actually happens

When the task finishes, open Scans → Reports and click into the report. Sort findings by severity (High / Medium / Low, driven by CVSS). For each high finding, read what it is, which CVE it maps to, and the suggested remediation. This is the deliverable an analyst hands off — a prioritized to-do list, not a verdict.

📸Screenshot for your report: the report sorted by severity, showing the high-severity findings.

⚠️ Where students get stuck

The usual snags.

[FEEDS STILL LOADING] OpenVAS needs a few minutes after startup to load its vulnerability feeds. Log in too early and scans find nothing or error. Wait, then refresh.
[TARGET IS 127.0.0.1] Docker forwards the target's ports to localhost, so the scan target is the loopback address, not the container's internal IP. Scanning the wrong address returns an empty report.
[THE SCAN "HANGS"] A full scan legitimately takes minutes. The task shows a progress percentage — let it run rather than restarting it.
[READING SEVERITY] Don't treat every finding as an emergency. Severity (CVSS) is there to prioritize; a Low on an isolated host may wait while a High on an exposed service jumps the queue.
[FALSE POSITIVES] Scanners infer from banners and responses and sometimes guess wrong. A finding is a lead to verify, not a confirmed breach.

🛡️ The defender's view

The scanner is a defensive tool — here's the program it belongs to.

Vulnerability management lifecycle

Breaks: the backlog of findings

Identify → prioritize → remediate → re-scan, on a schedule. A one-off scan is a snapshot; the program is the control.

Patch management

Breaks: most high findings

The majority of what OpenVAS flags on Metasploitable2 is missing patches. A current patch baseline removes whole swaths of the report.

Credentialed scanning

Breaks: blind spots

An authenticated scan sees installed software and config, not just exposed banners — far fewer false positives and far more coverage.

Risk-based prioritization

Breaks: too much to fix at once

CVSS plus asset value and exposure decides order. Fix the internet-facing High before the isolated Low.

Attack-surface reduction

Breaks: the findings' root

Every closed port, removed service, and decommissioned host is a finding that never appears. Less surface, shorter report.

Re-scan to verify

Breaks: “fixed” that wasn’t

Remediation isn't done until a follow-up scan confirms the finding is gone. Trust, then verify.

⚡ Cheat sheet

The scan, and what to do with it.

Run it

  • docker run -d -p 443:443 --name openvas mikesplain/openvas
  • docker run -ditP icarossio/metasploitable2
  • Config → Targets → 127.0.0.1
  • Scans → Tasks → run
  • Scans → Reports → sort by severity

Then

  • Prioritize by CVSS + exposure
  • Patch / reconfigure / isolate
  • Re-scan to verify
  • Prefer credentialed scans
  • Watch for false positives

Know the terms

  • CVSS — vulnerability severity score
  • CVE — a specific known flaw
  • False positive — flagged but not real
  • Credentialed scan — scanner logs in for depth

✅ Check yourself

1. A scan returns 40 findings. What have you actually accomplished, and what's left?

You've identified potential vulnerabilities — the first step only. Nothing is fixed. The work left is to validate (weed out false positives), prioritize by severity and exposure, remediate, and re-scan to confirm.

2. Why does a credentialed (authenticated) scan usually beat an unauthenticated one?

Logging in lets the scanner read installed packages, patch levels, and configuration directly instead of guessing from exposed banners — giving broader coverage and far fewer false positives.

3. Two findings: a High on an internet-facing web server and a High on an isolated lab host. Same score — do you treat them the same?

No. Severity is one input; exposure and asset value are others. The internet-facing service is reachable by attackers and should be remediated first. Risk-based prioritization, not raw score, drives the order.

4. Where does this scan sit in the vulnerability-management lifecycle?

At the 'identify' stage. The full cycle is identify → prioritize → remediate → re-scan/verify, repeated on a schedule — the scan is one turn of that wheel.
