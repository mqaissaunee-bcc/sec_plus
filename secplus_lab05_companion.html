Analyzing Types of Attacks and Mitigation Techniques

Three very different attacks back to back — a password brute force, a denial of service, and outright data destruction — each paired with the control that stops it. Matching an attack to its mitigation is the exact skill the exam tests.

📋 Overview

Three attack classes, three mitigations, one hour.

You'll run a password attack (ncrack hammering SSH), watch sshguard auto-block it by writing firewall rules; trigger a denial of service with a one-line fork bomb and watch the host choke; and study a destructive dd command that overwrites a disk. The point isn't the attacks — it's pairing each one with the right defense.

[ONE COMMAND IS IRREVERSIBLE] dd if=/dev/zero of=/dev/sda destroys the disk. In the pod that's recoverable by resetting; anywhere else it is not. Treat Phase 3 as something to understand, not to repeat casually.

5 Now, we start the sshguard on the UbuntuSRV system. Type the command below, followed by pressing the Enter key. If prompted for a password, type NDGlabpass123!. Press Enter. To double-check, you can confirm the sshguard status by running the service sshguard status command.

sysadmin@ubuntusrv:~$ sudo iptables -S Notice the last entry in the iptables was created to block the access from 203.0.113.2, which is our Kali machine (Feel free to ssh to the Ubuntusrv machine on Kali, it will fail until the 60-second block time is reached).

Task 2

Demonstrate DOS Attack

[NOTE] Warning: Do not attempt this section of the lab on a personal computer. It will cause serious harm to a machine, resulting in an inoperable state.

1 While on the Ubuntu system, type the command below followed by pressing the Enter key to monitor live CPU and memory usage within a Terminal window.

sysadmin@ubuntusrv:~$ htop

2 Open a new Terminal window. Right-click on the Terminal icon and click New Window.

3 Make sure to display the new Terminal window in a way where you can see both terminals side-by- side.

4 In the new Terminal window, type the command below to initiate a "fork bomb" attack on the Ubuntu system.

sysadmin@ubuntusrv:~$ :(){ :|: & };:
📸Screenshot for your report: DoS in action. htop/iotop during the fork bomb.

5 Watch closely at the Terminal window with htop running. After 3-4 minutes, notice how the CPU usage spikes, reaching almost 100% while both memory and swap memory spiking as well. What is happening here is that the UbuntuSRV system is running out of memory by forking a process infinitely. In other words, it is making multiple copies of itself that is setting off a chain reaction resulting in quickly exhausting the system's resources.

[NOTE] Because the system is overwhelmed, the htop application may be slow and unresponsive. Keep an eye on the Uptime value and see whether it is incrementing. If it is not, it is unresponsive. You may proceed to the next step.

6 When you are finished analyzing the "fork bomb" operation, click on the Ubuntu tab. Select the dropdown menu for Ubuntu and select Power Off.

7 In the pop-up window, answer Power Off.

8 Wait until the task finishes, and then click the Power On button.

9 Then, click the Power On button again in the pop-up window. Proceed to the next section.

⚠️ Where students get stuck

The traps in this one.

[NCRACK ARGUMENTS] You need the wordlist path (/usr/share/wordlists/fasttrack.txt) and -p ssh. A missing flag either errors or silently targets the wrong thing.
[SSHGUARD NOT ACTUALLY BLOCKING] Starting the service isn't enough — confirm the -N sshguard chain exists with iptables -S. No chain, no blocking.
[THE FORK BOMB FREEZES YOU] That's the demonstration, not a mistake. Recovery needs resource limits in place beforehand, or a reboot of the VM.
[TYPING THE FORK BOMB] Copy :(){ :|: & };: exactly — the : is the function name, and every symbol matters.
[dd IS FINAL] There is no confirmation and no undo. Only run it in the pod; understand the mitigation rather than rehearsing the command.

🛡️ The defender's view

The exam's real question: which control answers which attack?

Lockout / sshguard / fail2ban

Breaks: the brute force

Auto-ban source IPs after repeated failures — the iptables chain you watched sshguard build is exactly this, at the network layer.

Key-based auth + MFA

Breaks: brute force at the root

Disable password login entirely and there's no password to guess. The strongest answer to online password attacks.

Resource limits (ulimit / cgroups)

Breaks: the fork bomb

Cap processes, CPU, and memory per user so a single account can't exhaust the host — the fork bomb hits a ceiling instead of the whole machine.

Least privilege / sudo control

Breaks: the destructive dd

Ordinary accounts can't write to raw devices like /dev/sda. Tightly limiting who holds root is what stops the wipe.

Tested backups + immutability

Breaks: the dd impact

An offline or immutable backup turns a catastrophic erase into a restore. Untested backups don't count.

Monitoring & alerting

Breaks: detection for all three

Spikes in failed logins, process counts, or raw disk writes should alert the SOC before the attack finishes.

[THE PATTERN] Password attack → lockout/MFA. Resource exhaustion → limits. Destruction → least privilege + backups. Learn the mapping, not just the tools.

⚡ Cheat sheet

Three attacks, three fixes.

The attacks

  • Brute force: ncrack -v HOST --user U -P LIST -p ssh
  • DoS: :(){ :|: & };: (fork bomb)
  • Destroy: dd if=/dev/zero of=/dev/sda
  • Watch: htop, iotop, auth.log

What stops each

  • Brute force → sshguard/fail2ban, MFA, keys
  • Fork bomb → ulimit / cgroups
  • dd wipe → least privilege + backups
  • All three → monitoring + alerting

Know the terms

  • Brute force — trying every password
  • DoS — exhausting a resource
  • Fork bomb — self-replicating processes
  • sshguard — log-driven auto-ban

✅ Check yourself

1. How does sshguard defeat an SSH brute-force attack?

It reads the auth log for repeated failed logins and inserts iptables rules to block the offending source IP — lockout/rate-limiting enforced at the network layer.

2. The fork bomb has no exploit and no payload. Why is it still a serious attack?

It's resource exhaustion: recursive, self-replicating processes consume all available process slots, CPU, and memory until the system is unusable — a denial of service. The mitigation is per-user resource limits.

3. Which CIA properties does dd if=/dev/zero of=/dev/sda attack, and how do you defend against it?

Integrity and availability — it destroys the data and the system's ability to serve it. Defend with least privilege (non-root users can't write to the raw disk) and tested, restorable backups.

4. Match each of the three attacks to its CompTIA category and its mitigation.

Brute force = password attack → lockout/MFA/keys. Fork bomb = denial of service / resource exhaustion → resource limits. dd wipe = destruction / availability attack → least privilege + backups. Each category has its own control — that pairing is the exam skill.
