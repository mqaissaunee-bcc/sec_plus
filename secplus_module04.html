Vulnerabilities

Application, web, system, virtualization, and cloud vulnerability classes - what causes each, how they are exploited in principle, and the defences that actually address them.

Progress: 0% complete

Overview

[OBJECTIVES] By the end of this module you will be able to explain the major application vulnerability classes and what causes each; describe how injection and cross-site scripting work and why input validation is the common defence; identify operating system, firmware, hardware, and mobile weaknesses; explain virtualization and cloud-specific vulnerabilities including the shared responsibility model; and describe what makes a zero-day different from every other vulnerability.

Module 3 covered who attacks you and how they arrive. This module covers what they find once they get there. Objective 2.3 is a long list of vulnerability types, and the temptation is to memorise the list. That approach fails on scenario questions, which describe a symptom and expect you to name the cause.

Vulnerability, exploit, and patch

TermMeaning
VulnerabilityA weakness that could be exploited
ExploitThe technique or code that takes advantage of it
PatchThe vendor's correction that removes the weakness
Zero-dayA vulnerability with no patch available, because the vendor does not yet know

A vulnerability with no known exploit still carries risk, because someone may develop one. An exploit with no matching vulnerability in your environment carries none. This is the threat-and-vulnerability intersection from Module 3, applied to specifics.

The pattern beneath most of this module

An unexpectedly large share of vulnerability classes reduce to one idea: data supplied by a user was treated as an instruction. Buffer overflows, SQL injection, cross-site scripting, and memory injection are all versions of it. The system expected input and received something that changed its behaviour instead.

Once you see that pattern, the defences stop looking like a list to memorise. Input validation, parameterised queries, output encoding, and bounds checking are all the same instruction in different contexts: decide what input is acceptable, and treat everything else as data rather than obeying it.

📝 Think of it like…

A form with instructions written in the margin

A clerk receives a form with a box marked "Name". A customer writes "Jane Smith - and also empty the safe". A careful clerk copies the whole string into the name field and finds it odd. A careless clerk reads it as instructions and walks to the safe.

Every injection vulnerability is that careless clerk. The fix is never to ask customers to stop writing strange things; it is to build a process where anything in the Name box is treated as a name, whatever it says.

Where it breaks down: a clerk can use judgement about a strange request. Software has none - it does exactly what it is told, which is why the boundary between data and instruction has to be enforced by design rather than by vigilance.

[LEGAL AND ETHICAL] This module explains how vulnerabilities work so you can find and fix them. Testing any of it requires written authorization for the specific systems in scope. Scanning or probing systems you do not own is unlawful in most jurisdictions regardless of intent, and "I was learning" is not a defence.

Application Vulnerabilities

Buffer overflow

A buffer is a fixed-size region of memory reserved to hold data. A buffer overflow occurs when a program writes more data than the buffer was sized for, and the excess spills into adjacent memory that holds something else - other variables, or the address the program will return to when the current function finishes.

That return address is what makes overflows dangerous rather than merely buggy. If an attacker can control what overwrites it, they can redirect execution to code of their choosing. This is why buffer overflow is classed as a memory-safety issue with potential for arbitrary code execution rather than as a simple crash.

The root cause is a missing bounds check: the program accepted input without verifying it fit. Languages such as C and C++ leave bounds checking to the developer, which is why overflows are far more common there than in memory-safe languages that check automatically.

☕ Think of it like…

Pouring into a cup that is already full

You have a cup that holds 250ml and you pour in 400ml. The first 250 go where you intended. The rest goes across the counter, into the sugar bowl, and over the note reminding you where to go next.

The dangerous part is not the mess - it is that the note is now unreadable, and if someone chose what spilled onto it, they chose where you go next. That note is the return address, and the bounds check is simply measuring before you pour.

Memory injection

Memory injection is inserting code into the memory space of a running process, so the malicious code executes with that process's identity and privileges. Because the host process is legitimate and often trusted, this evades controls that decide what to allow based on which program is running.

The distinction from a buffer overflow is worth holding: an overflow is a specific flaw allowing memory to be corrupted, while memory injection describes the broader technique of getting code into another process's space. An overflow may be the means; injection is the objective.

Race conditions and TOCTOU

A race condition occurs when the result of an operation depends on the timing of events that were assumed to happen in a fixed order. The exam focuses on one variety: time-of-check to time-of-use, or TOCTOU.

The pattern is a program that checks a condition, then acts on the result of that check - with a gap in between. If an attacker changes the underlying state during that gap, the program acts on a fact that is no longer true. It verified that a file was safe, then opened a file that had been swapped in the meantime.

Race conditions are notoriously difficult to find in testing because they depend on precise timing and may occur only under load. The defensive approach is to make the check and the use a single atomic operation, so no gap exists for an attacker to act in.

🎬 Think of it like…

Booking the last cinema seat

Two people check the website at the same instant and both see "1 seat remaining". Both click Buy. The check was accurate when each made it, and the site sells a seat that does not exist - because between checking and buying, the world changed.

Fixing this is not about checking more carefully. It is about making the check and the purchase one indivisible step, so nothing can happen in between. That is exactly the remedy for TOCTOU.

Integer overflow and privilege escalation

An integer overflow occurs when an arithmetic result exceeds the maximum a variable can hold and wraps around, so a very large number becomes a very small or negative one. This matters when the result is used as a size: a length calculation that wraps to a small value causes a buffer to be allocated far smaller than the data about to be written into it, producing an overflow that no explicit length check would catch, because the check itself was fed the wrong number.

Privilege escalation is the outcome most application flaws are ultimately chasing. It comes in two directions. Vertical escalation gains higher privileges than the account holds - an ordinary user becoming an administrator. Horizontal escalation gains access to another account at the same privilege level, such as viewing a different customer's records by changing an identifier in a request.

Horizontal escalation is worth attention because it is easy to overlook. It involves no broken authentication and no elevated rights; the application simply never checked that the record being requested belonged to the person requesting it. The defence is an authorization check on every object access, not merely at login.

Malicious update

Update mechanisms are trusted by design - that is their purpose - which makes them an attractive thing to subvert. A malicious update reaches the target through the legitimate channel, signed and expected, exactly as in the supply chain attacks from Module 3.

The defences are code signing so that updates are verifiably from the vendor, staged rollouts so a bad update reaches a small population first, and monitoring for unexpected behaviour after installation. Note the limit of signing: it proves the update came from the vendor, not that the vendor was uncompromised when they signed it.

Web-Based Vulnerabilities

SQL injection

Web applications build database queries using values supplied by users. If those values are pasted directly into the query text, a user can supply input that changes the structure of the query rather than merely its parameters.

The classic illustration is a login form where the application builds a query from the username and password fields. Supplying a value containing ' OR '1'='1 can turn a condition that should match one account into one that is always true, because the quote character ends the intended value and everything after it is read as part of the query instead.

The consequences range from bypassing authentication to reading, modifying, or deleting the entire database, depending on the privileges the application's database account holds.

[NOTE] The example above is shown to explain the mechanism - the quote character escaping its intended context. Understanding that is what lets you recognise the defence. Actual exploitation of a system you do not own and have not been authorised to test is a criminal offence.

Why parameterised queries fix it

The instinctive fix is to filter out dangerous characters. This is fragile: encoding tricks, alternative syntax, and simple oversights defeat blocklists routinely.

The robust fix is parameterised queries, also called prepared statements. The query structure is defined first, with placeholders where values go, and the values are supplied separately. The database is told "this is the query, and these are data" as two distinct things, so a value containing a quote is simply a value containing a quote. It cannot alter structure because structure was already fixed.

This is the deepest lesson in the module: the fix is not better filtering but a design in which data cannot become instruction.

Cross-site scripting

Cross-site scripting, or XSS, occurs when an application includes user-supplied content in a page without properly encoding it, so a browser interprets that content as script rather than text. The script then runs in the victim's browser with the privileges of the site it appears to come from - which is what makes session theft and impersonation possible.

TypeWhere the payload livesWho is affected
ReflectedIn a crafted link or request; echoed back immediatelyWhoever follows the link
StoredSaved on the server, in a comment or profile fieldEvery visitor who views it
DOM-basedNever reaches the server; handled entirely by client-side scriptWhoever triggers the client-side path

Stored XSS is the most severe of the three because it requires no interaction beyond visiting a legitimate page, and it affects everyone who does. The distinguishing question in an exam scenario is where the payload resides: in a link, in the database, or only in the browser.

📋 Think of it like…

A notice pinned to a trusted noticeboard

A community noticeboard is trusted because it is maintained by the council. Someone pins a notice reading "Building policy has changed - hand your keys to the man in the blue coat." Residents comply, because they trust the board and never considered that anyone can pin anything to it.

That is stored XSS. The malicious content is served by a site the victim trusts, which is why their browser runs it with that site's privileges. Reflected XSS is the same notice handed directly to one person; DOM-based is a notice the reader assembles themselves from instructions they were given.

Defending against XSS

DefenceWhat it does

Note that output encoding is the primary defence rather than input validation. The same string may be harmless in one context and dangerous in another, so the safest point to make that decision is where the content is written into a page.

Cross-site request forgery

Cross-site request forgery, or CSRF, exploits the fact that a browser automatically attaches cookies to requests for a site. If a user is logged into their bank in one tab and visits a malicious page in another, that page can cause a request to be sent to the bank - and the browser helpfully includes the session cookie, so the bank sees an authenticated request the user never intended to make.

Note carefully how CSRF differs from XSS, since exam options often offer both. XSS runs attacker script within the trusted site. CSRF sends a request to the trusted site from elsewhere, and the attacker never sees the response - they can cause an action but cannot read the result. The defence is an anti-CSRF token: a value the legitimate page includes that an attacker cannot predict or read.

Directory traversal and other injection

Directory traversal manipulates file path input to reach files outside the intended directory, typically using sequences that navigate upward through the filesystem. It is the same failure in a different context: input that was supposed to name a file within a folder instead described a path elsewhere.

Injection as a family extends beyond SQL - command injection, LDAP injection, and XML injection all follow the identical pattern. Recognising the family is more useful than memorising each member.

✉ Think of it like…

A signed blank cheque in your pocket

Your browser carries your session cookie the way you might carry a signed cheque - it is attached automatically to anything sent to that bank. A stranger who cannot reach into your pocket can still hand you a letter that causes you to post the cheque to them.

That is CSRF. The attacker never holds your cheque and never sees what the bank sends back. They simply arranged for a request to be made that carried your signature. An anti-CSRF token is the bank additionally requiring a reference number that only its own letters contain.

Operating System, Hardware, and Mobile

Operating system vulnerabilities

The operating system sits beneath every application, so a flaw there undermines everything above it. OS vulnerabilities matter disproportionately for two reasons: kernel-level code runs with the highest privilege, and the operating system is the component enforcing separation between users and processes. A flaw that breaks that separation defeats controls that were otherwise correctly configured.

Privilege escalation is the characteristic outcome. An attacker who gains ordinary user access uses an OS flaw to become an administrator, at which point most other controls on that host become advisory.

Firmware

Firmware is the low-level software embedded in hardware - the BIOS or UEFI on a motherboard, the controller on a drive, the code inside a router or camera. It runs before the operating system, which means malicious firmware persists through reinstalling the OS and even through replacing the disk.

Firmware is difficult in practice for reasons that have nothing to do with its technical nature. It is rarely inventoried, updates are inconsistent and often manual, and many organizations have never patched the firmware on a device they have run for years.

🏗 Think of it like…

The foundations under a house

You repaint rooms, replace the boiler, and refit the kitchen. Nobody inspects the foundations, because reaching them is disruptive and they have always been fine. A problem down there is not fixed by redecorating - every room above inherits it.

Firmware sits in that position. Reinstalling the operating system is redecorating; it leaves the foundation exactly as it was, which is why firmware implants are prized by sophisticated attackers.

End-of-life and legacy systems

An end-of-life system is one the vendor no longer supports, so no patch will ever be issued for any vulnerability discovered from that point onward. A legacy system is outdated but may still receive limited support.

The distinction the exam draws is between a vulnerability that can be fixed and one that structurally cannot. Every future flaw in an end-of-life system is permanent. This is the canonical compensating control scenario: isolate the system on a restricted segment, limit which accounts can reach it, and increase monitoring around it, because the primary control - patching - is unavailable forever.

🚗 Think of it like…

A car with no parts left in production

The car still drives. But when the brake assembly fails there is no replacement, because the manufacturer stopped making them a decade ago. You can drive it more carefully, keep it off motorways, and inspect it more often - but you cannot fix the brakes.

Driving more carefully is the compensating control. It reduces risk genuinely, and it is not the same as a repair, which is why end-of-life systems belong on a replacement plan rather than a maintenance schedule.

Hardware and supply chain vulnerabilities

Hardware can be vulnerable through design flaws in processors, components that leak data through side channels, or tampering before delivery. The objective names supply chain vulnerabilities across three routes: service providers with access to your systems, hardware providers whose components may be tampered with, and software providers whose updates you trust.

Hardware supply chain compromise is the hardest to detect because the organization has no realistic means of inspecting a component at the silicon level. Defence relies on sourcing from vetted suppliers and monitoring for unexpected behaviour rather than on inspection.

Jailbreaking is worth understanding properly. The security of a modern mobile platform rests on the operating system enforcing that applications cannot read each other's data and only signed code runs. Jailbreaking removes those enforcement mechanisms, so a jailbroken device is not slightly weaker - it has had its principal security architecture switched off.

⚙ Think of it like…

Removing the guard from a machine

Industrial machinery ships with a guard over the blade. It is inconvenient - it slows the work and gets in the way - and an experienced operator can remove it and work faster for years without incident.

The guard was not there for the experienced operator on a good day. It was there for the moment something slips. Jailbreaking removes the guard, and the device works fine right up until the day it does not.

Virtualization and Cloud

Virtual machine escape

Virtualization runs multiple guest machines on one physical host, with a hypervisor enforcing isolation between them. VM escape is a flaw allowing code in a guest to break that isolation and reach the hypervisor or other guests.

This is severe because the entire model assumes isolation holds. Organizations routinely place workloads of different sensitivity on shared infrastructure on exactly that assumption. An escape invalidates it, and in a multi-tenant cloud the neighbouring guest may belong to a different company entirely.

🏨 Think of it like…

A tenant breaking through the wall

A block of flats works because the walls hold. Tenants accept living beside strangers on the understanding that nobody can walk through plasterboard into the next flat, or into the building manager's office where every key is kept.

VM escape is a tenant who finds they can. The severity is not that one flat was entered - it is that the assumption underpinning the entire building was wrong, including for everyone who never met the attacker.

Resource reuse

Cloud and virtualized platforms constantly reallocate memory and storage between customers. Resource reuse is the vulnerability that arises when those resources are not properly cleared before reassignment, so one tenant receives storage or memory still containing another tenant's data.

Providers address this with sanitisation on release. The tenant-side defence is encryption: data encrypted before it reaches shared infrastructure remains unreadable even if a fragment surfaces elsewhere.

🛍 Think of it like…

A hotel room that was never cleaned

You check in and find the previous guest's papers in the desk drawer. Nobody broke in and nobody attacked you - housekeeping simply skipped a step between occupancies.

That is resource reuse. It is also why the guest-side answer is to carry nothing readable: if your papers were in a locked case, what housekeeping missed would not matter.

Cloud-specific vulnerabilities and the shared responsibility model

The most common cloud vulnerability is not exotic. It is misconfiguration: storage left publicly accessible, over-permissive identity policies, management interfaces exposed to the internet, logging never enabled.

Misconfiguration is so prevalent partly because the shared responsibility model is widely misunderstood. The provider secures some layers and the customer secures others, and where the line falls depends on the service model.

ModelProvider securesCustomer secures
IaaSPhysical, network, hypervisorOS, applications, data, access
PaaSThe above plus OS and runtimeApplications, data, access
SaaSNearly the whole stackData, access, and configuration

Note the constant across all three rows: data and access control are always the customer's responsibility. No service model transfers them. Assuming the provider handles security generally is the single most common origin of cloud breaches.

🏠 Think of it like…

Renting a flat

The landlord maintains the roof, the structure, and the entrance door to the building. You lock your own front door and decide who gets a key. If you leave your door open and are burgled, the landlord's excellent roof is not the issue.

Cloud misconfiguration is nearly always a door left open by the tenant. The provider's infrastructure worked perfectly - which is why "the cloud was breached" is usually an inaccurate description of what happened.

Where it breaks down: a tenant can see their own front door. A cloud misconfiguration may be a permission buried three levels deep in a policy nobody has read, which is why automated configuration scanning matters more here than vigilance.

Containers and serverless

Containers package an application with its dependencies and share the host operating system kernel rather than running a full guest OS. That makes them fast and light, and it also makes their isolation weaker than a virtual machine's: containers on a host share a kernel, so a kernel flaw can allow a container escape more readily than a hypervisor flaw allows a VM escape.

Container-specific weaknesses cluster in a few places. Images are frequently built on public base images that carry known vulnerabilities. Containers are often run as root because it is simpler. And because containers are treated as disposable, they are rebuilt from an image rather than patched - which means an unpatched base image reproduces the same vulnerability every time it is deployed.

Serverless functions shift more responsibility to the provider, since there is no operating system for the customer to manage. The customer's remaining exposure concentrates in application code, dependencies, and - most commonly - the permissions granted to the function.

Over-permissive identity and API exposure

Cloud identity policies are the most consequential configuration a customer controls, and over-permissioning is endemic. Policies are often granted broadly during development to make something work and never narrowed, so a compromised function or instance can reach far more than its job requires. This is least privilege from Module 1 applied to machine identities, and it is the difference between a contained incident and an account-wide one.

APIs deserve separate mention because cloud services are operated almost entirely through them. An API endpoint exposed without authentication, or with authentication but no authorization check on each object, provides direct programmatic access to data. Horizontal privilege escalation is especially common here, because APIs frequently accept an identifier and return the corresponding record without verifying the caller should see that particular one.

Zero-Days and Countermeasures

Zero-day vulnerabilities

A zero-day is a vulnerability unknown to the vendor, so no patch exists. The name refers to the number of days the vendor has had to respond. What makes it distinct is not that it is more severe technically, but that the primary defence - patching - is unavailable to anyone.

Zero-days are expensive to find and are therefore used selectively. This connects directly to Module 3: an unskilled attacker will not have one, while a nation-state may hold several. If a scenario describes an organization compromised through a flaw with no available patch, it is also telling you something about the actor.

🔑 Think of it like…

A flaw the lock manufacturer has not heard of

Someone discovers that a particular lock opens if you turn the key a certain way. The manufacturer does not know. No locksmith can help you, because there is no recall and no replacement cylinder - the flaw is not yet a known problem.

You can still put a bar across the door, keep valuables elsewhere, and notice when the door opens at three in the morning. That is what defence against zero-days looks like: not prevention of the unknown flaw, but layers that limit and reveal its use.

The patch gap

Most exploited vulnerabilities are not zero-days. They are flaws with patches that were published months earlier and never applied. The window between a patch being released and being deployed is the patch gap, and publication of a patch often makes exploitation easier - the fix reveals what the flaw was, and working exploits frequently appear within days.

This produces a conclusion students find counter-intuitive but the exam expects: patching promptly matters more than defending against unknown flaws. The realistic threat is a known vulnerability you have not yet closed.

Running a patch management process

Knowing that patching matters is not the same as being able to do it at scale. A workable process has a recognisable shape.

StageWhat happens
InventoryKnow what you run, including versions and dependencies
MonitorTrack vendor advisories and vulnerability feeds
PrioritiseRank by exploitability and exposure, not by score alone
TestVerify the patch in a representative environment
StageDeploy to a small population first
DeployRoll out broadly within a defined window
VerifyConfirm the patch actually applied everywhere

The last stage is skipped more often than any other, and it is where organizations acquire false confidence. A patch that failed silently on forty machines produces a report saying the vulnerability is closed while forty systems remain exposed. Verification is what turns a patch deployment into a patch remediation.

Prioritisation deserves a note too. A high-severity flaw in a system with no network exposure may matter less than a medium-severity flaw in an internet-facing service under active exploitation. Severity scores describe the vulnerability in isolation; risk depends on your environment, which is the Module 3 intersection again.

When you cannot patch immediately

Sometimes a patch exists but cannot be applied on the required timescale - a system that cannot take downtime, an application the vendor has not yet certified against the update, a change freeze. The interim answer is virtual patching: blocking exploitation at a layer in front of the vulnerable system, typically with a web application firewall or IPS signature that recognises the exploit pattern.

Virtual patching buys time and does not fix anything. The vulnerability remains, the workaround may be bypassed, and the exam treats it the way it treats compensating controls generally - legitimate, deliberate, and temporary. An answer presenting it as a permanent substitute for patching is wrong.

How vulnerabilities become known

Vulnerabilities reach vendors through several routes, and the exam expects you to distinguish them. Responsible disclosure gives the vendor a private window to fix the flaw before details are published. Bug bounty programmes formalise this by paying researchers, which both encourages reporting and creates a legitimate channel that would otherwise not exist. Full disclosure publishes immediately, on the argument that users deserve to know and vendors move faster under pressure - at the cost of arming attackers before a fix exists.

A bug bounty is also a security control in a sense worth noticing: it changes the economics of what a researcher does with a discovery, offering a lawful and paid alternative to selling it.

Dependency scanning deserves particular emphasis. Modern applications are assembled largely from third-party libraries, so most of the code in a typical application was written by someone else. A vulnerability in a widely used library becomes a vulnerability in thousands of applications at once, and organizations frequently do not know which of their systems include it - which is the software equivalent of the missing asset inventory from Module 3.

[EXAM] When a scenario asks for the best defence against injection, prefer the answer that changes the design (parameterised queries, output encoding) over the one that adds filtering. Blocklists are consistently the weaker option.
