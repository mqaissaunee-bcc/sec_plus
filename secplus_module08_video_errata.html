Errata: Secure Baselines, Hardening, and Asset Management videos

The five explainer videos for Module 8 were AI-generated from the Module 8 reading. They are a good overview, but they contain a few errors and leave out several exam-relevant points. When a video and the reading disagree, the reading is correct: Security+ Module 8.

If you read nothing else

  1. The one universal hardening technique is changing default credentials. Isolation is not part of it. Video 2 adds "and isolate the device" to that answer. "Change defaults and isolate" is the approach for IoT devices specifically.
  2. HttpOnly does not stop cross-site scripting. It limits the damage by keeping scripts from reading the cookie. The injected script still runs (Video 4).
  3. A code signature proves the code came from whoever holds the signing key. That is not the same as proving who the publisher is. A stolen key produces a valid signature (Video 4).
  4. Failed drives that can't be overwritten must be destroyed, whatever their sensitivity. Destruction methods are shredding, degaussing, and incineration (Video 5).
  5. Several exam terms appear in none of the videos: EAP, secure boot, host-based firewall, embedded/RTOS systems, degaussing, and the Domain 4 exam weight (28%). See the checklist.

01 · Security Operations Starts with a Secure Baseline

8:10 · Module sections: Overview, Secure Baselines

Clarification07:18–07:30

Infrastructure as code "gives drift almost zero opportunity to accumulate."

Rebuilding from a definition gives drift less opportunity to accumulate. It doesn't eliminate drift, so you still need configuration enforcement and monitoring.

Minor01:33–01:46

The building-code analogy uses "10,000 houses using 400 different people over a decade."

The reading says a thousand houses built by four hundred people. The point is the same: a careful individual doesn't scale, and a standard does.

Missing from Video 1

  • Exam weight and objectives. Domain 4 (Security Operations) is 28% of the exam, the largest domain. This module covers objective 4.1 (applying security techniques to computing resources) and 4.2 (asset management). The two go together because you can't apply a baseline to a system you don't know exists.
  • How to deploy. The video explains how deployment fails but not how it should be done: ideally at build time, through automation, and applied to the existing systems as well as new ones.
  • CIS Benchmarks have graded levels. They aren't one setting for everyone.
  • Exception versus drift. The video says a documented adjustment is what separates a thoughtful exception from a mistake. The reading goes further: a documented, justified deviation is a baseline exception, and an undocumented one is configuration drift.
  • The lifecycle is a loop. Drift findings feed back into revising the baseline (Establish → Deploy → Maintain → Establish).

02 · Hardening Techniques

6:42 · Module section: Hardening Targets and Techniques

Correction05:46–06:02

The question asks for the single technique that applies to every class of target. The answer given is "You change the default credentials and isolate the device."

The universal technique is changing default credentials, with nothing added. It needs no agent, no patch, and no vendor support. "Change defaults and isolate" is the right approach for IoT devices, but you don't isolate a managed workstation on its own network segment, so isolation isn't universal. The video's own explanation (06:02) only justifies the credentials part.

Minor01:43–01:50

Changing default credentials removes "the simplest, most common attack factor."

"Factor" should be vector. The reading calls it "the simplest vector in the curriculum." It doesn't claim it is the most common.

Clarification04:16–04:34

Cloud logs should be exported to a separate account.

That's correct but incomplete. Logs go to a separate account with different credentials, and they must be retained long enough to investigate. Also, cloud logging is often disabled by default, which is why "enable at account creation" matters.

Missing from Video 2

  • The full hardening toolkit. The video covers removing software, disabling ports, changing defaults, and least functionality. It never mentions host-based firewall or secure boot (only signed boot code runs), and it doesn't cover patch management on a defined cycle or logging and monitoring as toolkit items.
  • Embedded systems and RTOS are never mentioned. In the reading they're a separate target class: network isolation and vendor firmware updates. Agents are impossible, and often so is any update at all.
  • Why ICS/SCADA gets passive monitoring. Active scanning can crash fragile controllers. ICS/SCADA can't take patching, agents, or active scanning.
  • Other target rows. Servers emphasize least functionality, baselines, and a host firewall. For switches and routers, change defaults, disable unused ports, and secure the management plane, because you can't install agents. With cloud infrastructure you can't access the layers the provider operates. IoT devices sometimes can't even be inventoried.
  • The pattern behind it. When a technique isn't possible on the device, controls move around the device. This is the compensating control pattern from Module 1.
  • The management plane is broader than switches. It also covers hypervisors, cloud consoles, and storage arrays. Old unencrypted protocols should be disabled, not just deprioritized, because of downgrade attacks (Module 5).
  • Cloud configuration. Misconfiguration is the leading cloud finding, which is why automated scanning against a baseline matters. All three cloud areas are on the customer side of the shared responsibility model (Module 4).
  • Half the practice set. The video works 3 of the 6 scenarios. The others are:
    ScenarioApproach
    Networked camera with factory password and no firmware updatesChange defaults and isolate
    Core switch whose management is reachable from the user VLANSecure the management plane
    Employee-owned phone with corporate emailMDM and containerization
    Production Linux server with unused default servicesLeast functionality and baselines

03 · Securing Wireless Networks and Mobile Devices

7:51 · Module section: Wireless and Mobile

Clarification03:55–04:04

Enterprise authentication "is an absolute requirement for modern organizations."

The exam rule is narrower. Enterprise mode (individual authentication against RADIUS) is the answer whenever a scenario mentions staff turnover or needs to revoke one user without affecting anyone else. Personal mode (pre-shared key) still exists and is still tested.

Clarification05:12–05:17

CYOD "offers a nice middle ground from an approved list."

The middle ground is about choice, not ownership. In CYOD the organization owns the device and has high control. Employees just pick from an approved list. Only BYOD is employee-owned.

Clarification07:01–07:09

Bluetooth introduces pairing attacks "if it's just carelessly left on indefinitely."

The specific weakness is leaving Bluetooth discoverable indefinitely, not just leaving it on.

Minor06:46–06:51

"Cellular connections are generally the most controlled and secure path."

The reading says "generally the most controlled path." It makes no claim that cellular is inherently secure.

Missing from Video 3

  • EAP is never mentioned. EAP is the framework that carries credentials (passwords, certificates, tokens) in enterprise wireless authentication. It appears in the reading's wireless settings table.
  • What else a site survey finds: existing networks already present, interference, and channel overlap. These affect availability, and availability is a security property.
  • MDM restricts applications as well as deploying them.
  • Exam rule. When a BYOD scenario needs corporate data removed, the answer is a selective or container wipe, never a full device wipe.
  • Link back. The rogue access point and evil twin risks come from Module 5.

04 · Application Security, Sandboxing, and Monitoring

8:36 · Module section: Application Security, Sandboxing, and Monitoring

Correction02:11–02:25

The HttpOnly attribute "is a huge defense against cross site scripting."

HttpOnly does not prevent XSS. It makes the cookie unreadable to client-side script, which limits the damage a successful XSS can do (no session-token theft). The injected script still runs. Input validation and output encoding are what prevent XSS. Expect exam options built around this difference.

Clarification04:54–05:02

Code signing "proves exactly who published the software."

A signature proves the software came from the holder of that signing key and hasn't changed since signing. If the key is stolen, or the publisher is compromised (a supply chain attack, Module 3), malware gets a valid signature. A signature also says nothing about whether the software is safe. That's why signature verification and behavioral monitoring after installation are both required.

Clarification06:15–06:33

"Sandboxing is about containment, not outright prevention. Actually, scratch that. It's more like a temporary holding cell…"

The self-correction is confusing, and the first statement was the right one. Sandboxing is detection and containment rather than prevention. Sandbox-aware malware can stay dormant while it's being watched, so a clean sandbox result is weaker evidence than it looks. That's why sandboxing complements endpoint monitoring rather than replacing it.

Minor03:05–03:13

Static analysis catches flaws "before the software is even compiled."

What defines static analysis is that it examines code without running it, early in development. Some SAST tools also analyze compiled code.

Minor07:01–07:07

"As the source material perfectly puts it…"

This is left over from how the video was generated. The "source material" is the Module 8 reading.

Missing from Video 4

  • The third operational form of sandboxing: separating development and test environments from production. The video only covers detonating attachments and isolating browser tabs.
  • The operational framing. Module 4 covered these as fixes for specific vulnerabilities. Objective 4.1 treats them as controls applied across an estate.
  • Why publisher-based allow lists work. Allowing "signed code from approved publishers" is far easier to maintain than listing individual files (Module 5). Code signing is the Module 2 digital signature applied to executables.
  • The missing-logs indicator. Logs that aren't forwarded off the host can be erased. Missing logs are a Module 5 indicator of compromise.

05 · Asset Management

8:00 · Module section: Asset Management

Clarification05:38–05:47

For "a failed drive that literally can't be overwritten… physical destruction like shredding is mandatory for highly sensitive data."

The video merges two separate cases. Destruction is right for (1) highly sensitive data and (2) failed media. A drive too damaged to overwrite can't be sanitized, so destruction is the only option however sensitive the data is. Destruction methods include shredding, degaussing, and incineration.

Clarification02:01–02:10

Without asking about end of support, "you literally just bought a very expensive paperweight."

The real danger is the opposite. The device keeps working, so it stays in service while it can't be patched. Example from the reading: a device bought with three years of security updates and used for eight is unpatchable for five years. Ask at purchase how long the vendor will issue security updates.

Minor01:22–01:31

The lifecycle runs from "purchase on day one to assignment in week one…"

The timings are only for illustration and don't come from the reading or any standard. The four phases are Acquisition → Assignment → Monitoring/Tracking → Disposal.

Missing from Video 5

  • Warranty returns. A failed drive sent back to the vendor under warranty leaves with its data intact unless that's negotiated in advance.
  • Phantom inventory entries. The video stresses undiscovered assets. The reading points out that the other direction matters too: inventory entries for assets that no longer exist create false assurance that something was decommissioned when it may still be running.
  • Location includes cloud region, which matters for data sovereignty.
  • Why certification matters. Without a certificate of destruction, the organization can't demonstrate to a regulator that the data was removed. Scenarios mentioning regulators or audits want certification named.
  • Legal holds. Destroying a device that holds records under a legal hold is a serious problem. Keeping data past its purpose is liability with no benefit (Module 7).
  • Classification ties to the data classification work in Module 7.

Checklist: exam points the videos skip

If you only watched the videos, make sure you can explain each of these from the reading.

  • Domain 4 is 28% of the exam. This module covers objectives 4.1 and 4.2.
  • Baselines are deployed at build time through automation, to existing systems as well as new ones.
  • A documented deviation is an exception. An undocumented one is drift.
  • Secure boot and host-based firewall are hardening techniques.
  • Embedded systems / RTOS: network isolation and vendor firmware. Agents (and often updates) are impossible.
  • ICS/SCADA: no patching, no agents, no active scanning. Use segmentation and passive monitoring.
  • The only universal technique is changing default credentials.
  • EAP carries credentials (passwords, certificates, tokens) in enterprise wireless.
  • CYOD is organization-owned. Only BYOD is employee-owned.
  • BYOD + remove corporate data → selective/container wipe, never a full wipe.
  • HttpOnly limits XSS damage. It doesn't prevent XSS.
  • A code signature proves key holder + integrity, not safety.
  • Sandboxing is detection and containment, and it complements endpoint monitoring.
  • Destruction methods: shredding, degaussing, incineration. Failed media must be destroyed.
  • Warranty returns leave with data intact unless negotiated.
  • Deletion ≠ sanitization. Certification is the evidence regulators want.
