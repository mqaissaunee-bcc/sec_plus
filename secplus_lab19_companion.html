Working with Android

📋 Overview

Small device, big exposure.

Mobile devices store email, accounts, photos, and often corporate data — and they leave the building every day. This lab walks the core Android security settings: screen lock, network settings, privacy and app permissions, and browser settings. None of it is flashy; all of it is the baseline that determines whether losing the phone means losing the data on it.

[THE ONE IDEA] On mobile the threat model is loss and theft first. Screen lock plus device encryption is what turns a stolen phone into a useless brick instead of an open filing cabinet.

🧭 The walkthrough

A settings tour — the point is knowing which settings matter and why.

Phase 1 · Screen lock

The first and most important control

Set a strong screen lock (PIN, password, or biometric) and add a lock-screen message (helps a finder return a lost phone). On modern Android a screen lock also gates device encryption — without it, the data is far more exposed. This single setting does the most work.

📸Screenshot for your report: the screen lock configured and the lock-screen message set.
Phase 2 · Network settings

Where it connects

Review Wi-Fi behavior — forgetting open/untrusted networks and controlling auto-connect reduces exposure to rogue access points and on-path attacks (the wireless and capture labs show why that matters).

Phase 3 · Privacy & permissions

What the apps can see

Walk the privacy settings and app permissions. Apps accrete access they don't need — location, microphone, contacts. Pruning permissions to what each app actually requires is least privilege applied to a phone.

📸Screenshot for your report: the app-permissions / privacy review.
Phase 4 · Browser settings

The most-used app

Check the Chrome settings (safe browsing, warnings) and the 'add users from lock screen' control. The browser is where most mobile risk arrives, so its settings are part of the baseline.

⚠️ Where students get stuck

It's a tour — here's how to get value from it.

[KNOW WHY, NOT JUST WHERE] The exam cares about which control stops which threat, not the exact menu path. For each setting, ask: what attack does this blunt?
[LOCK MESSAGE ≠ DATA PROTECTION] A lock-screen message aids recovery of the device; it doesn't protect the data. The lock itself (and encryption) does that.
[PERMISSION CREEP] Granting a permission once leaves it on. The checkup is about revoking what apps no longer need, not just reviewing.
[THIS SCALES TO MDM] Everything you set by hand here is what an enterprise enforces centrally with MDM — connect the individual settings to the fleet-level control.
[UPDATES MATTER MOST OF ALL] No setting substitutes for a patched OS and apps — out-of-date mobile software is a common entry point.

🛡️ The defender's view

Individual settings here are exactly what enterprises enforce at scale.

Screen lock + device encryption

Breaks: lost/stolen phones

The core mobile control: a locked, encrypted device protects its data when it leaves your hands. Everything else is secondary to this.

MDM / MAM

Breaks: unmanaged fleets

Mobile Device/Application Management enforces these settings centrally, separates work from personal data, and enables remote lock/wipe across every device.

App permissions + store-only installs

Breaks: over-permissioned / malicious apps

Least privilege for apps, and installing only from vetted stores (no sideloading) — the direct defense against the kind of APK built in Lab 01.

Timely updates

Breaks: unpatched known flaws

Out-of-date mobile OS and apps are a prime entry point. Enforce prompt patching, by policy where possible.

Remote wipe / find

Breaks: irrecoverable loss

When a device is truly gone, remote wipe protects the data and remote-find aids recovery — part of every mobile baseline.

Avoid untrusted networks

Breaks: rogue APs / sniffing

Controlling Wi-Fi behavior and using a VPN on the move limits exposure to the on-path attacks the wireless labs demonstrate.

⚡ Cheat sheet

The mobile baseline.

The checkup

  • Strong screen lock + lock message
  • Review Wi-Fi / network behavior
  • Prune app permissions
  • Browser safe-browsing settings
  • Keep OS + apps updated

Enterprise scale

  • Screen lock + encryption (the core)
  • MDM/MAM for central control
  • Store-only installs, no sideloading
  • Remote wipe / find
  • VPN on untrusted networks

Know the terms

  • MDM / MAM — manage devices / apps
  • Sideloading — installing outside the store
  • Remote wipe — erase a lost device
  • Containerization — split work/personal

✅ Check yourself

1. A phone is lost. What single control most determines whether this is a breach?

A strong screen lock backed by device encryption. Locked and encrypted, the data is inaccessible to whoever finds it; without it, the phone is an open filing cabinet.

2. Why is installing only from official app stores part of the mobile baseline?

Store apps are vetted, and blocking sideloading prevents malicious apps (like the APK payload in Lab 01) from being installed. It's application allow-listing for the phone.

3. You set all these controls by hand on one device. How does an enterprise do it for thousands?

Through MDM/MAM — Mobile Device/Application Management — which enforces the settings centrally, separates corporate from personal data, and enables remote lock and wipe across the whole fleet.

4. The lab has you add a lock-screen message. Does that protect the data? What does?

No — a lock-screen message only helps a finder return the device. The data is protected by the screen lock and device encryption, not by the message.
