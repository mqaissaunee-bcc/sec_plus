Performing Active Reconnaissance

Before anyone attacks a network they map it: which hosts are alive, which ports are open, what software answers. This lab does that mapping with PowerShell on Windows and nmap on Linux — and shows why a firewall makes a live host look dead.

⏱ ~50 min 📶 Difficulty: Intermediate 🧰 Tools: nmap · PowerShell 🎯 Targets: the pod's hosts & subnets 📘 Maps to: Module 9 — Vulnerability Management, Monitoring, and Enterprise Controls
[AUTHORIZED TESTING ONLY] Active reconnaissance sends packets to systems and is detectable and often illegal without authorization. Scanning hosts or networks you do not own or have written permission to test is a crime in most jurisdictions.

📋 Overview

The difference between active and passive — and why it matters.

Passive reconnaissance reads what's already public and touches nothing. Active reconnaissance — this lab — sends packets at the target and watches the replies, which is far more informative and far more detectable. You'll enumerate a Windows host with PowerShell, then use nmap from Linux to sweep for live hosts, scan ports, fingerprint services, and guess operating systems. The payoff is a map of the attack surface; the catch is that every scan is noise an IDS can hear.

[THE ONE IDEA] When nmap says a host is down, it often isn't — a firewall is just dropping the ping. -Pn ("don't ping, assume up") is the flag that reveals hosts hiding behind that behavior.

Task 1

Use PowerShell to Perform an Active Reconnaissance of a Windows Server

In this section, you will utilize PowerShell on the Windows server to gather extensive information.

1 Launch the WinOS virtual machine to access the graphical login screen.

2 While on the splash screen, focus on the NETLAB+ tabs. Click the dropdown menu for the WinOS tab and click on Send CTRL+ALT+DEL.

3 Log in as administrator using the password NDGlabpass123!.

4 Leave the Server Manager window untouched (or you can minimize it). Then, right-click on the Windows logo in the taskbar and click Windows PowerShell (admin).

5 In the PowerShell window, type the command below, followed by pressing the Enter key.

PS C:\Users\Administrator> $cred=Get-Credential

6 Notice a pop-up window appears. Type Administrator in the User name field, followed by typing NDGlabpass123! in the Password field. Click OK.

7 Back on the PowerShell prompt, enter the command below to retrieve a list of domain users on the system.

PS C:\Users\Administrator> Get-ADGroupMember -Credential $cred -server WinOS "Domain Users" | select samaccountname

8 Enter the command below to identify which users are Domain Admin Members.

PS C:\Users\Administrator> Get-ADGroupMember -Credential $cred -server WinOS "Domain Admins"

9 Filter the SAM account names.

PS C:\Users\Administrator> Get-ADGroupMember -Credential $cred -server WinOS "Domain Admins" | select samaccountname

10 View the domain itself.

PS C:\Users\Administrator> Get-ADDomain

11 See whether the lab2-user account is currently enabled.

PS C:\Users\Administrator> Get-ADUser -filter 'samaccountname -eq "lab2-user"'

12 Not only do we see that the account lab2-user is enabled, but we also have the account's SID as well. Try to retrieve more information about the Administrator account by entering the command below.

PS C:\Users\Administrator> Get-ADUser -filter 'samaccountname -eq "administrator"'

13 View the lab-user account user's group memberships and confirm whether the account belongs to the Domain Admins group.

PS C:\Users\Administrator> Get-ADPrincipalGroupMembership lab-user
[NOTE] It can be verified that the lab-user is part of the Domain Admins group as well as other groups.

14 Type cls, and press Enter; leave the PowerShell window open to continue with the next task.

Task 3

Scanning the Network for Vulnerable Systems

In this section, you will utilize nmap on the Linux machine to gather network information.

1 Launch the Kali virtual machine to access the graphical login screen.

2 Log in as kali with kali as the password.

3 Open a new terminal and view the available options that can be used with Nmap by typing nmap into the terminal followed by pressing the Enter key.

4 Initiate a quick ping scan to identify live hosts with a network ID of 172.16.1.*.

kali@kali$ nmap -sP 172.16.1.*
[NOTE] You should see two host results; 172.16.1.1 as the DMZ gateway, and 172.16.1.10 as Ubuntu Server.

5 Initiate a ping scan while spoofing the source MAC address at the same time.

kali@kali$ nmap -v -sP -spoof-mac 0 172.16.1.*

6 When scanning for active systems on a network, Nmap also gives the ability to scan for which IP protocols are supported by the host involved in the scanning process. Enter the command below, and enter the password kali when prompted.

kali@kali$ sudo nmap -PO 172.16.1.10

7 In the Terminal window, select File from the top menu pane and click on New Tab.

8 While engaged in the new tab, initiate a Transmission Control Protocol (TCP) scan against the SecOnion system. Type the following command:

kali@kali$ nmap -sT 192.168.0.6

9 Notice that the scan came back stating that the host seemed to be down and that it was unable to scan it. Attempt another scan against the same system, but this time using the no ping option.

kali@kali$ nmap -PN 192.168.0.6
[NOTE] After 2-3 minutes, notice that nmap scan now states that the host is up but that the first 1000 ports are being filtered; most likely due to a firewall.

10 Initiate an operating system scan against the pfSense system to help identify what version of OS it is running on.

kali@kali$ sudo nmap -O 192.168.0.1

11 Notice that the nmap scan returned with a host is down message. Scan the host again, this time, using the -PN option to identify whether the host is actually up or down.

kali@kali$ nmap -PN 192.168.0.1
[NOTE] After 2-3 minutes, notice that nmap scan now states that the host is up but that the first 1000 ports are being filtered.

12 Initiate the same scan from the previous step but this time against the UbuntuSRV system.

kali@kali$ sudo nmap -O 172.16.1.10
[NOTE] Notice that Nmap has a tough time trying to identify the operating system information.

13 To try and gather more information about the same host regarding its OS, make Nmap take approximate guesses as to what the OS is by using the command below with an included script.

kali@kali$ sudo nmap -O --osscan-guess 172.16.1.10

14 Initiate a scan specifically for port 80, but this time for all hosts on both networks (Internal & DMZ).

kali@kali$ nmap -p 80 192.168.0.0/24 172.16.1.0/28

15 Scan the UbuntuSRV system while at the same time displaying all packets being sent and received while initiating the scan.

kali@kali$ nmap --packet-trace 172.16.1.10

16 Nmap can also be used to show local host data about which interfaces are up and what the route table looks like. Enter the command below.

kali@kali$ nmap --iflist

17 To detect remote services, both services and daemons, along with their respective version numbers, initiate the Nmap command below.

kali@kali$ nmap -sV 172.16.1.10

18 The lab is now complete; you may end the reservation.

⚠️ Where students get stuck

The flag confusion that trips people up.

[“HOST IS DOWN” BUT IT ISN’T] A firewall dropping ICMP makes nmap skip the host. Re-run with -Pn to scan it anyway — this is the single most common surprise in the lab.
[-sP vs -sV vs -O] They answer different questions: -sP/-sn = who's alive, -sV = what service/version, -O = which OS. Mixing them up wastes a scan.
[ROOT FOR -O] OS and SYN scans need raw sockets — run them with sudo, or nmap quietly falls back and the results change.
[CIDR MATH] /24 is 256 addresses; /28 is 16. Get the mask wrong and you either miss hosts or scan far more than intended.
[SCANS ARE SLOW — AND LOUD] Version and OS scans take time and generate obvious traffic. That's realistic: active recon is detectable by design.

🛡️ The defender's view

You can't stop someone sending packets — but you can see them and shrink what they find.

Attack-surface reduction

Breaks: the whole scan

Every closed port and disabled service is one less thing to find. The smallest footprint wins; most of what nmap reports is something that didn't need to be exposed.

Firewall / default-deny

Breaks: host & port discovery

Dropping unsolicited probes is what made hosts look 'down.' A default-deny posture forces an attacker to work harder and noisier.

IDS / IPS

Breaks: the scan itself

Suricata/Snort recognize sweep and version-scan patterns. Active recon is detectable — alerting on it buys early warning before the attack.

Service & banner hardening

Breaks: version fingerprinting

Patch and configure services, and suppress verbose banners, so -sV can't hand an attacker exact versions and their CVEs.

Network segmentation

Breaks: lateral mapping

VLANs and ACLs limit what any one vantage point can scan, so a foothold can't map the whole estate.

Rate limiting / tarpits

Breaks: fast enumeration

Throttling or tarpitting connections slows a scan to a crawl and makes it even easier to spot.

⚡ Cheat sheet

The nmap flags that matter.

Scan types

  • -sn / -sP — ping sweep (who's up)
  • -Pn — skip ping, assume up
  • -sT — TCP connect scan
  • -sV — service/version detection
  • -O — OS fingerprint (needs sudo)
  • -p 80 — specific port(s)

What stops / spots it

  • Attack-surface reduction (close ports)
  • Firewall default-deny (drops probes)
  • IDS/IPS alerts on scan patterns
  • Banner/version hardening
  • Segmentation + rate limiting

Know the terms

  • Active vs passive — send packets vs observe only
  • Host discovery — who's alive
  • Fingerprinting — identifying OS/service
  • Attack surface — everything reachable

✅ Check yourself

1. nmap reports a host as 'down,' but you're sure it's running. What's happening and what do you do?

A firewall is likely dropping the ICMP ping nmap uses for host discovery, so nmap skips it. Re-run with -Pn to bypass the ping check and scan the host anyway.

2. What's the difference between -sV and -O, and why run both?

-sV identifies the service and version answering on a port; -O infers the operating system. Together they complete the attack-surface picture — what's listening and what it's running on.

3. Active recon is noisy. Name the defensive upside of that.

Because it sends detectable packets, an IDS/IPS can recognize sweep and version-scan patterns and alert — giving defenders early warning before an attack follows the recon.

4. A defender can't stop an attacker from sending packets. What can they control?

The attack surface and visibility: close unneeded ports and services, default-deny at the firewall, harden banners so versions leak less, segment the network, and alert on scan activity. You shrink what's findable and make the looking obvious.
