Malicious Activity and Mitigation

Malware taxonomy, network, password, cryptographic and physical attacks, reading indicators of compromise, and the mitigation and hardening techniques that address each.

Progress: 0% complete

Overview

[OBJECTIVES] By the end of this module you will be able to classify malware by how it spreads and what it does; explain the major network, password, cryptographic, and physical attacks; read indicators of compromise and say what each suggests; and select the mitigation and hardening techniques that actually address a given attack.

This module completes Domain 2. Module 3 covered who attacks and how they arrive, Module 4 covered the weaknesses they find, and this module covers what they actually do - and what you do about it. Objectives 2.4 and 2.5 are paired deliberately: the first is a catalogue of malicious activity, the second the catalogue of mitigations, and the exam expects you to move between them.

How to hold this much vocabulary

This is the longest list of named things in Domain 2, and rote memorisation is the wrong approach. Two organising questions handle most of it.

For malware, ask: how does it spread, and what does it do once it arrives? Those two axes are independent, and almost every malware term in the objective is a point on that grid.

For attacks, ask: what is the attacker abusing? Nearly every technique abuses either trust in an identity, trust in a protocol, or a resource limit. Once you can name what is being abused, the mitigation follows without needing a separate list.

A note on overlap with Module 4

Objective 2.4 lists application attacks - injection, buffer overflow, directory traversal, privilege escalation - that were covered in depth in Module 4 as vulnerabilities. That is not a duplication in the objectives so much as a change of viewpoint. Module 4 asked what weakness exists; this module asks what an attacker does with it and how you notice.

Where those techniques appear here, the emphasis is on recognition and response rather than mechanism. If you need the mechanism, it is in Module 4 and worth rereading rather than relearning.

🔍 Think of it like…

A doctor working from symptoms

A patient does not arrive announcing a diagnosis. They arrive with a fever, a rash, and fatigue, and the clinician works backward from the combination to the cause - because any one symptom alone fits a dozen conditions.

Indicators of compromise work exactly this way. A single failed login means almost nothing. Failed logins across two hundred accounts, each attempted once, from one address, means something quite specific. The skill this module builds is reading the combination.

[LEGAL AND ETHICAL] This module describes attack techniques so you can recognise and defend against them. Conducting any of these against systems you do not own, without written authorization defining scope, is a criminal offence in most jurisdictions. Curiosity is not authorization.

Malware

Two independent questions

Malware terminology confuses students because the terms describe different things and are then used as though they were alternatives. Some name a propagation method, and some name a payload. A single specimen has both.

QuestionTerms that answer it
How does it spread?Virus, worm, trojan
What does it do?Ransomware, spyware, keylogger, rootkit, logic bomb

So "a worm that delivers ransomware" is not a contradiction - it is a complete description, naming both axes. Exam options frequently mix the two, and recognising which question an option answers eliminates distractors quickly.

Propagation: virus, worm, trojan

TypeHow it spreadsNeeds user action?
VirusAttaches to a host file; spreads when that file is run or sharedYes
WormSelf-propagating across a network with no host fileNo
TrojanDisguised as something desirable; the user installs itYes

The worm is the one that matters most operationally, because removing the human from the loop removes the speed limit. A virus spreads as fast as people share files; a worm spreads as fast as the network allows, which is why worm outbreaks are measured in minutes.

🦠 Think of it like…

A hitchhiker, a runner, and a gift

A virus is a hitchhiker. It cannot travel on its own - it needs to be inside something you were already carrying, and it moves only when you do.

A worm is a runner. It needs nobody's help and no vehicle. It finds the next door itself and keeps going while everyone sleeps, which is why containment is about closing routes rather than warning people.

A trojan is a gift you carry inside yourself, past every guard, because you wanted it. No perimeter control was defeated - you opened the door and held it.

Payload: what it does once it arrives

PayloadBehaviourCharacteristic indicator
RansomwareEncrypts data and demands paymentMass file modification, ransom note, resource inaccessibility
SpywareCovertly collects informationUnexpected outbound traffic
KeyloggerRecords keystrokesCredential compromise with no obvious breach
RootkitHides its own presence, often at kernel levelDiscrepancies between tools; missing logs
Logic bombDormant until a condition is metNothing, until it triggers
BloatwareUnwanted preinstalled softwareNot malicious, but expands attack surface

Bloatware is worth a moment because it is the odd one out. It is not malicious and has no attacker behind it - it is preinstalled software nobody asked for. It appears in the objective because unnecessary software is unnecessary attack surface, which links directly to the hardening techniques later in this module.

🔒 Think of it like…

Someone changing your locks and selling you the key

You come home and your key no longer works. Nothing has been taken - every possession is exactly where you left it, visible through the window. A note on the door offers to sell you the new key.

This captures why ransomware is an availability attack rather than a confidentiality one, and why backups are the answer. If you have a second house containing copies of everything, the person holding your key has nothing to sell. Paying is buying back access to things you already own.

Where it breaks down: modern ransomware usually copies the data before encrypting it and threatens publication. That turns it into a confidentiality attack too, which is why good backups no longer fully neutralise the threat.

Rootkits and why they are different

A rootkit's payload is concealment. It operates at a privileged level - often the kernel, sometimes firmware as covered in Module 4 - and manipulates what the system reports so its files, processes, and network connections do not appear.

The consequence is that a compromised system cannot be trusted to report on itself. Directory listings, process lists, and logs all pass through code the rootkit controls. This is why detection relies on comparing what the system reports against an external view - booting from trusted media, or noticing that traffic seen at the network boundary does not appear in the host's own logs.

📋 Think of it like…

A building inspector who signs off on their own work

You ask the inspector whether the wiring is safe and they say yes. The certificate is genuine, the paperwork is in order, and the inspector is the person who did the wiring.

A rootkit is that inspector. Asking a compromised machine to report on itself returns an answer written by the thing you are trying to find, which is why the remedy is an independent inspector - a boot from trusted media, or a view from the network rather than the host.

Logic bombs and insiders

A logic bomb lies dormant until a condition is met - a date, a particular file changing, or an account disappearing from a directory. That last trigger is the classic insider pattern: code that activates when the author's own account is disabled, so the damage occurs after they have left.

Logic bombs are difficult to detect because there is nothing to observe until they fire. Defences are procedural rather than technical - code review, separation of duties so no one person can deploy unreviewed code, and change management from Module 1.

Network Attacks

Denial of service and distributed denial of service

A denial of service attack makes a resource unavailable to legitimate users. A distributed denial of service uses many sources at once, typically a botnet, which both multiplies volume and makes blocking by source address impractical.

Two refinements appear in the objective and are frequently confused. Reflected attacks send requests to third-party servers with the victim's address forged as the source, so responses go to the victim. Amplified attacks choose protocols where a small request produces a large response, multiplying the traffic. They are usually combined: a small forged request to many servers produces a flood of large responses aimed at the victim.

📬 Think of it like…

Ordering catalogues in someone else's name

You post a thousand reply cards to catalogue companies, writing your neighbour's address in the return field. Each card is a postcard; each catalogue is two kilograms.

Your neighbour receives a van-load of mail from companies who did nothing wrong and have no idea they participated. That is reflection - the return address was forged - and amplification, since a postcard produced a parcel. Note the defensive implication: the catalogue companies are the ones who can fix this, by not honouring requests they cannot verify.

Reflection and amplification

On-path attacks

An on-path attack - previously called man-in-the-middle - places the attacker between two communicating parties, able to read and modify traffic while both believe they are talking directly to each other.

The enabling conditions are worth knowing because they point at the defences: unencrypted traffic, encrypted traffic where certificate warnings are ignored, and network positions an attacker can occupy such as a rogue wireless access point. Properly validated TLS defeats on-path attacks, which is why certificate warnings matter and why clicking through them is more consequential than users assume.

🗣 Think of it like…

A dishonest interpreter

Two people who share no language negotiate through an interpreter. Each speaks freely, believing they are heard accurately. The interpreter relays most of it faithfully and changes the number in the contract.

Neither party can detect this from inside the conversation - everything sounds coherent. What defeats it is not listening harder; it is both parties holding something the interpreter cannot forge, which is precisely what a validated certificate provides.

DNS attacks

DNS translates names into addresses, and it is trusted almost universally without verification. DNS poisoning inserts false records so a name resolves to an attacker's address. Domain hijacking takes control of the registration itself. DNS tunnelling abuses DNS queries as a covert channel to move data out of a network, exploiting the fact that DNS is almost always permitted outbound.

DNS tunnelling is a good example of an indicator worth recognising: unusually large volumes of DNS traffic, or queries to a single domain with long random-looking subdomains, are characteristic.

📞 Think of it like…

Someone editing the phone directory

You look up your bank's number in a printed directory and dial it. The number connects to someone who answers with the bank's greeting. You did nothing careless - you consulted the reference everyone uses and it had been altered.

DNS poisoning is that edit. It also explains why the defence is authentication rather than caution: DNSSEC signs records so a forged entry can be detected, and TLS means the wrong destination cannot present a valid certificate for the name you asked for.

Replay and credential replay

A replay attack captures valid data in transit and retransmits it to produce an effect the attacker was not authorised to cause. Credential replay captures an authentication exchange and replays it to log in without ever knowing the password.

The defences are what make an intercepted exchange useless the second time: session tokens that expire, nonces or timestamps that make each exchange unique, and encryption preventing capture in the first place.

🎤 Think of it like…

A recording of you saying the password

A voice-activated door opens when you say a phrase. Someone records you saying it and plays the recording back the next day. They never learned anything; they reused something you already said.

The fix is not a longer phrase. It is a door that says a different random word each time and requires you to respond to that word - which is exactly what a nonce does.

Wireless and malicious code

Wireless attacks include rogue access points impersonating a legitimate network, evil twin attacks where the rogue duplicates a known network name, and deauthentication attacks that force clients to reconnect - typically so they reconnect to the attacker's network.

The objective also lists malicious code as a network attack, meaning code delivered and executed across the network rather than through a file a user opened. In practice this covers exploitation of network-facing services, which is the delivery mechanism for most worm propagation.

Password, Cryptographic, and Physical Attacks

Brute force and password spraying

These two are constantly confused, and the distinction is simply which variable is held constant.

AttackApproachWhat it triggers
Brute forceMany passwords against one accountAccount lockout, quickly
Password sprayingOne common password against many accountsAlmost nothing
Dictionary attackA curated word list against an accountLockout, but faster than pure brute force
Credential stuffingUsername and password pairs leaked elsewhereSuccessful logins, no failures

Password spraying exists specifically to evade lockout policies. A lockout after five failed attempts stops brute force cold, but an attacker trying one password against two thousand accounts generates one failure per account and locks nobody out. In an organization of that size, someone is using a predictable password.

Credential stuffing is worth separating because it produces no failed logins at all when it succeeds. The credentials are genuine - reused from a breach elsewhere - so the indicator is not failure but success from an unexpected location. This is why multifactor authentication is the controlling defence rather than password complexity.

🔑 Think of it like…

One key on every door, not every key on one door

A burglar trying a thousand keys on your front door is noticed - you find scratches, neighbours see someone loitering, and eventually the lock jams. That is brute force, and the lockout is the jam.

A burglar walking down a street of two thousand houses trying the same common key once at each door draws no attention anywhere. No individual household sees anything unusual. Someone's door opens, and nobody noticed - which is why detecting spraying requires looking across accounts rather than at any one of them.

Brute force versus spraying, as the defender sees it

Cryptographic attacks

These target the implementation rather than the mathematics, which is the Module 2 lesson restated.

AttackWhat it does
DowngradeForces both parties to negotiate a weaker protocol or cipher both still support
CollisionFinds two inputs producing the same hash, breaking integrity guarantees
BirthdayA statistical technique making collisions far easier to find than intuition suggests

The birthday attack name comes from the birthday paradox: in a room of just 23 people, there is a better than even chance two share a birthday. The counter-intuitive part is that you are not looking for a match to one specific person but for any match, and the number of possible pairs grows much faster than the number of people. Applied to hashing, finding any two inputs that collide takes far less work than finding an input matching one specific hash - which is why hash output length must be substantially larger than intuition suggests.

Downgrade attacks are the practical one. If a server supports both a modern protocol and a deprecated one for compatibility, an attacker who can influence negotiation forces the weak option. The defence is removal rather than de-prioritisation: a protocol still enabled can still be negotiated.

💬 Think of it like…

Insisting on a language you both half-remember

Two colleagues fluent in a modern shared language also each studied an older one at school. A third party insists the meeting be held in the old language "for compatibility". Both agree, because they can technically manage - and now the eavesdropper understands everything, because the old language is one they know well.

The fix is not speaking the old language more carefully. It is declining to speak it at all, which is why disabling deprecated protocols beats merely preferring modern ones.

Physical attacks

AttackDescription
Brute force (physical)Forcing a physical barrier - a door, a lock, an enclosure
RFID cloningReading a proximity badge and duplicating it onto blank media
EnvironmentalAttacking power, cooling, or fire suppression to cause failure

RFID cloning is the one most likely to appear in a scenario. Older proximity cards transmit a fixed identifier with no authentication, so a reader concealed in a bag can capture a badge from a short distance in a lift or a queue, and the identifier is then written to a blank card. The countermeasure is cards using cryptographic challenge-response rather than a static identifier, backed by a second factor at sensitive doors.

Environmental attacks connect to availability from Module 1. A data centre whose cooling fails is unavailable regardless of how well its data is encrypted, which is why environmental controls are security controls and not merely facilities management.

💳 Think of it like…

Photocopying a badge in the lift

An older proximity badge is a card that shouts its number whenever asked. Standing beside you in a lift, someone with a concealed reader asks - and your badge answers, because it has no way to tell who is asking or to refuse.

A modern credential works differently: the reader poses a challenge and the card must compute a response using a secret it never transmits. Overhearing the exchange gains nothing, because the next challenge will be different.

Indicators of Compromise

Objective 2.4 asks you to analyze indicators, not merely list attacks. Exam questions describe observed symptoms and ask what is happening. This section is the translation table.

The indicators named in the objective

IndicatorWhat it typically suggests
Account lockoutBrute force or dictionary attack against that account
Concurrent session usageCredentials in use by more than one person
Blocked contentAttempted access to known-malicious destinations
Impossible travelLogins from locations too far apart for the time elapsed
Resource consumptionExfiltration, cryptomining, or a denial of service attempt
Resource inaccessibilityRansomware encryption, or a successful denial of service
Out-of-cycle loggingActivity at times the account is never normally used
Published or documentedYour data appearing publicly or offered for sale
Missing logsDeliberate deletion to conceal activity

Two indicators that mean more than they appear to

Missing logs is the strongest single indicator in the list. Logs do not delete themselves, and a gap where entries should be is not an absence of evidence - it is evidence. It also implies the attacker had sufficient privilege to alter logging, which places the incident at a later and more serious stage than most other indicators.

Impossible travel is powerful because it is nearly unambiguous. A login from London at 09:00 and from São Paulo at 09:20 cannot both be the same person, whatever the explanation offered. The common false positive is a VPN or corporate proxy changing the apparent location, which is why tuning matters - but the underlying logic is sound and rarely produces genuine ambiguity.

💳 Think of it like…

Two card payments an hour apart, a continent apart

Your bank calls because your card paid for coffee in Manchester at nine and a television in Toronto at ten. The bank does not need to know which transaction was fraudulent to know something is wrong - the pair cannot both be you.

That is impossible travel, and it explains why the indicator is so useful: it requires no judgement about whether an individual action looked suspicious. The contradiction does the work.

Why a baseline comes first

Every indicator in the table above is a deviation from normal, which means none of them can be evaluated without knowing what normal is. "Out of cycle logging" requires knowing the hours an account is usually active. "Resource consumption" requires knowing what this server's CPU usually does at three in the morning. Without a baseline, an analyst is looking at numbers with nothing to compare them against.

This is why establishing a baseline appears repeatedly across the exam and why it precedes detection work. An organization that cannot say what its normal traffic volume looks like cannot recognise an abnormal one, and will either miss real incidents or drown in alerts about routine behaviour.

Baselines also expire. A workforce that shifts to remote working changes every location and hours-based indicator at once, and a detection rule tuned against the old baseline will fire constantly. Reviewing baselines after significant operational change is part of keeping detection useful rather than ignored.

False positives, false negatives, and alert fatigue

TermMeaningConsequence
True positiveAn alert for something genuinely maliciousThe system working
False positiveAn alert for benign activityWasted effort, and eventually distrust
False negativeMalicious activity that produced no alertThe dangerous failure
True negativeBenign activity correctly not alertedThe normal case

False negatives are worse in principle, but false positives cause more real-world failures. An analyst facing hundreds of daily alerts that turn out to be nothing begins dismissing them quickly, and eventually dismisses a real one. This is alert fatigue, and it explains why tuning detection rules is security work rather than housekeeping - a rule nobody trusts provides no protection regardless of how well it detects.

The practical balance depends on context. A rule watching a handful of highly sensitive systems can tolerate false positives; the same rule across ten thousand endpoints cannot.

Reading combinations

Individual indicators are weak; combinations are strong. These groupings recur in exam scenarios.

Combination observedMost likely explanation
One failed login across hundreds of accounts, one sourcePassword spraying
Many failures on one account, then a lockoutBrute force or dictionary attack
Successful login, unusual location, no failuresCredential stuffing or stolen credentials
Mass file modification, then inaccessibilityRansomware
High outbound traffic to one destination overnightData exfiltration
Sustained CPU load with no matching workloadCryptomining
Large DNS volume with long random subdomainsDNS tunnelling
Network traffic absent from host logsRootkit concealment

The last row rewards attention. The indicator is not something present but a disagreement between two sources. When a host and the network boundary describe different realities, the host is the one that cannot be trusted.

Correlation and threat intelligence

Individual indicators arrive from different systems - the firewall, the directory, the endpoint agent, the mail gateway. Correlation is the work of assembling them into one picture, which is what a SIEM exists to do. The impossible-travel finding earlier in this section is only possible because two authentication events from different times and places were compared; neither event alone was remarkable.

Threat intelligence supplies indicators observed elsewhere - addresses, domains, file hashes, and behavioural patterns seen in other organizations' incidents. Its value is that it lets you detect something you have never seen before because someone else already did. Its limitation is that indicators like addresses and hashes are cheap for an attacker to change, so intelligence based on behaviour ages far better than intelligence based on specific values.

Mitigation and Hardening

Objective 2.5 is the mitigation catalogue. Most of these appeared as concepts in earlier modules; here they are applied to specific attacks.

Allow lists versus deny lists

This distinction is high-yield and recurs across the exam. A deny list blocks what is known to be bad and permits everything else. An allow list permits what is explicitly approved and blocks everything else.

Allow listing is substantially stronger because it does not require knowing about a threat in advance. Novel malware is blocked not because it was recognised but because it was not on the list. Deny listing fails against anything new by definition - which is the same argument that made parameterised queries beat character filtering in Module 4.

The cost is operational. Allow lists require maintenance every time legitimate software changes, and organizations abandon them when that burden is not resourced. The exam expects you to know allow listing is stronger and that its weakness is administrative rather than technical.

📝 Think of it like…

A guest list versus a list of banned people

A doorkeeper with a banned list must recognise every troublemaker in the city, and anyone not yet known to them walks in. A doorkeeper with a guest list needs to know only who was invited; every stranger is turned away automatically, including ones nobody has heard of.

The guest list is obviously stronger. It is also more work, because someone must keep it current - and a guest list nobody updates causes legitimate guests to be turned away, which is exactly why allow listing fails in practice when it fails.

Hardening techniques

TechniqueEffect
EncryptionProtects data at rest on the endpoint
Endpoint protection / EDRDetects and responds to malicious behaviour on the host
Host-based firewallControls traffic to and from the individual host
HIPSBlocks recognised attack behaviour at the host
Disabling ports and protocolsRemoves services that were never needed
Changing default passwordsCloses the simplest vector in the entire curriculum
Removing unnecessary softwareEliminates bloatware and unused applications

Notice how these connect back. Removing unnecessary software addresses the bloatware from the malware section. Disabling unused ports addresses the open service ports from Module 3. Changing defaults addresses what is consistently the highest-return, lowest-effort control available.

Endpoint protection: signatures and behaviour

Traditional antivirus matched files against signatures of known malware. That is a deny list, with the weakness deny lists always have: anything not yet catalogued passes. Attackers defeat it cheaply by making trivial changes that alter the file without altering what it does.

EDR - endpoint detection and response - watches behaviour instead. Rather than asking whether this file matches something known bad, it asks whether this process is doing something a legitimate process would not: encrypting files rapidly across many directories, injecting into another process, or clearing event logs. Behaviour is far more expensive for an attacker to change than a file hash, because changing it means changing what the malware actually does.

The response half matters too. EDR can isolate a host from the network while leaving it running for investigation, which preserves evidence that a straightforward power-off would destroy.

Isolation and sandboxing

Isolation separates something from everything else, and it appears in the objective in several forms. A suspicious file can be detonated in a sandbox - a disposable environment where its behaviour is observed safely. An unpatchable system can be isolated on a restricted segment, the compensating control pattern from Module 4. A compromised host can be isolated during incident response so it stops communicating without being destroyed.

These are the same principle at three scales: analysis, ongoing risk management, and incident response. Recognising them as one idea is more useful than treating them as three separate terms.

Decommissioning properly

Decommissioning appears in the mitigation list because a system that no longer exists cannot be attacked. Done badly, though, it creates new exposure rather than removing it.

StepWhy it matters
Identify dependenciesSomething may still rely on this system
Revoke credentials and certificatesOtherwise they remain valid and usable
Remove DNS and firewall entriesStale records can be claimed by someone else later
Sanitise storageData must not survive on retired media
Update the asset inventoryOtherwise the system remains on paper and is never verified gone

The DNS step causes real incidents. A record pointing at cloud infrastructure that has been released can later resolve to whatever the provider assigns that address next, allowing someone else to receive traffic intended for a name your organization still publishes.

AttackMost direct mitigation

[EXAM] Two patterns are worth memorising. When credentials are genuine - stuffing, spraying that succeeded, insider misuse - the answer is multifactor authentication rather than password policy. And when an attack spreads after initial compromise, the answer is segmentation rather than better perimeter defence.
