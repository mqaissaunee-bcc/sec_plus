Security+ Lab Companion · Lab 03

Analyzing Types of Web Application Attacks

The two web attacks the exam asks about most: SQL injection, which tricks a database query into handing over data it shouldn't, and cross-site scripting, which gets a victim's browser to run the attacker's script. Both come from the same mistake — trusting user input.

⏱ ~60 min 📶 Difficulty: Intermediate 🧰 Tools: WebGoat · DVWA · Burp Suite · sqlmap 🎯 Target: web containers (172.17.0.2) 📘 Maps to: Module 5 — Malicious Activity and Mitigation
[AUTHORIZED TESTING ONLY] These attacks run against deliberately vulnerable apps (WebGoat, DVWA) inside an isolated pod. Injecting SQL or script into web applications you don't own or have written permission to test is a crime in most jurisdictions.

📋 Overview

Two attacks, one root cause.

SQL injection happens when user input is pasted straight into a database query, so an attacker's text becomes part of the SQL command. Cross-site scripting (XSS) happens when a page echoes user input back without encoding it, so an attacker's <script> runs in another user's browser. You practice SQLi in WebGoat's guided lessons, then against a realistic login challenge using Burp Suite's Repeater, then in DVWA — and finish with XSS.

[THE ONE IDEA] Both attacks exist because the app failed to keep data and code separate. Every fix below is some version of "treat input as data, never as instructions."

⚠️ Where students get stuck

The snags, in order of how often they bite.

[CASE-SENSITIVE URL] /WebGoat/login is case-sensitive, and the container's IP is 172.17.0.2:8080 — if it's different, check the container's actual address.
[UNBALANCED QUOTES] Injection is quote arithmetic. Count the quotes so the final query is valid SQL — one stray quote and you get a syntax error, not a dump.
[BURP INTERCEPT ON] Leave Intercept off so pages load, then work from HTTP history. With Intercept on, the browser just hangs.
[KEYRING / PASSWORD PROMPTS] When Firefox offers to save the password or asks for a keyring, choose Never / Cancel — they interrupt the flow.
[XSS WON'T FIRE] The input has to be reflected or stored unescaped. If you see the literal <script> text on the page, the app is encoding output — that field isn't vulnerable.

🛡️ The defender's view

Each attack above is an app that forgot to separate data from code.

Parameterized queries

Breaks: SQL injection

Prepared statements bind input as data, so it can never change the query's structure. This is the one fix the exam wants named first.

Input validation (allow-list)

Breaks: SQLi & XSS

Reject unexpected characters at the boundary — accept only what a field legitimately needs rather than trying to block every bad string.

Output encoding + CSP

Breaks: cross-site scripting

Encode on output so <script> renders as visible text, and a Content-Security-Policy blocks inline/untrusted scripts from executing.

Least-privilege DB account

Breaks: SQLi impact

The web app's database user shouldn't be able to read every table or run DROP/DELETE — limiting it caps the damage an injection can do.

WAF

Breaks: both (defense in depth)

Signatures catch ' or 1=1 and <script>, buying time — but a WAF is a filter in front of the real fix, not the fix.

Secure SDLC + testing

Breaks: the root cause

Code review and SAST/DAST (sqlmap is an attacker's DAST) catch these before release. Build security in rather than bolting it on.

⚡ Cheat sheet

The payloads and their fixes.

Attack strings

  • SQLi: ' or '1'='1 · 0 or 1=1
  • Burp: capture POST → Repeater → edit → Send
  • Automate: sqlmap -u "<url>"
  • XSS: <script>alert(1)</script>

What stops it

  • Parameterized queries (SQLi — the fix)
  • Input validation / allow-listing
  • Output encoding + CSP (XSS)
  • Least-privilege DB account
  • WAF (defense in depth)

Know the terms

  • SQLi — input becomes part of the query
  • XSS — input becomes script in a browser
  • Reflected vs stored — crafted link vs saved on server
  • DAST — testing the running app (sqlmap)

✅ Check yourself

1. Why does ' or '1'='1 return every row?

It closes the string literal the query expected, then adds a condition that is always true, OR'd into the WHERE clause — so every row satisfies it and the query returns the whole table.

2. SQL injection and XSS both come from trusting input. Who is the victim in each, and where does the attacker's code run?

SQLi: the database/server is the victim and the injected code runs in the SQL engine. XSS: another user is the victim and the injected script runs in their browser.

3. What is the definitive fix for SQL injection, and why isn't a WAF enough?

Parameterized (prepared) queries — they bind input as data so it can't alter the query's structure. A WAF only pattern-matches known payloads and can be bypassed, so it's a supporting layer, not the fix.

4. What keeps a stored XSS payload from executing in a visitor's browser?

Encoding the data on output so it displays as text instead of running, backed by a Content-Security-Policy that restricts which scripts the browser will execute.
