Setting Up a Load Balancer

One server is a single point of failure; two behind a load balancer is resilience. This lab builds exactly that — two web servers and a balancer in front — then shows traffic spreading across them and service surviving when one goes down.

📋 Overview

Availability, built from redundancy.

A load balancer sits in front of several identical servers and spreads incoming requests across them. Two things come for free once it's there: scale (more servers share the work) and failover (if one server dies, the balancer routes around it and users never notice). You'll set up a web server on Windows (IIS) and one on Ubuntu (Apache), put a balancer in front, then watch requests alternate and survive a server failure.

[THE ONE IDEA] Load balancing is an availability control — the 'A' in the CIA triad. Its job isn't speed so much as making sure the service stays up when a component doesn't.

The lab's own example names the catch: if a user's shopping cart lives on one server and the balancer sends their next request to another, the cart's gone. That's why session persistence (sticky sessions) exists — a concept worth knowing by name.

⚠️ Where students get stuck

Where the build snags.

[PORT 80 CONFLICT] Only one web server can bind port 80. Stop nginx before starting Apache, or the service won't come up.
[IDENTICAL PAGES] If both backends serve the same page you can't tell the balancer is working. Make each page clearly name its server.
[BROWSER CACHING] Refreshes may be served from cache, hiding the switch. Force-reload (Ctrl+Shift+R) so you actually hit the balancer each time.
[HEALTH CHECK LAG] Failover isn't instant — the balancer has to notice the backend is down via its monitor. Give it a moment after stopping a service before judging.
[THE STICKY-SESSION TRAP] Without session persistence, stateful apps break when requests bounce between servers. The lab's shopping-cart example is the exam's favorite illustration.

🛡️ The defender's view

Load balancing is an availability control — here's the architecture around it.

Redundancy / high availability

Breaks: single point of failure

Multiple backends mean no one server failing takes the service down. This is the core resilience pattern behind the 'A' in CIA.

Health checks / failover

Breaks: routing to dead servers

Active monitors let the balancer stop sending traffic to a failed backend automatically — failover only works if the balancer knows a server is down.

Session persistence

Breaks: broken stateful sessions

Sticky sessions keep a user pinned to one backend so logins and carts survive. Know when you need it — and that it trades away some even distribution.

Scheduling algorithms

Breaks: uneven load

Round-robin, least-connections, weighted — the method should match the workload so no backend is overwhelmed while others idle.

SSL/TLS termination

Breaks: crypto overhead & visibility

Balancers often terminate TLS, centralizing certificate management and letting them inspect/route — a design choice with security trade-offs to weigh.

The balancer is a target too

Breaks: new single point of failure

The balancer itself must be redundant (a pair) and hardened — otherwise you've just moved the single point of failure to the front door.

⚡ Cheat sheet

Spread it, survive failure.

The build

  • Two web servers (unique pages)
  • service nginx stop → service apache2 start
  • Pool of backends + virtual server
  • Health check / monitor
  • Refresh to see distribution; stop one to see failover

Design for it

  • Redundancy = high availability
  • Health checks drive failover
  • Session persistence for stateful apps
  • Pick the right scheduling method
  • Make the balancer itself redundant

Know the terms

  • Load balancer — spreads requests over backends
  • Failover — route around a dead server
  • Round-robin — rotate requests evenly
  • Sticky session — pin a user to one backend
  • High availability — stays up through failures

✅ Check yourself

1. Which part of the CIA triad does a load balancer primarily serve, and how?

Availability. By spreading requests across redundant backends and routing around any that fail, it keeps the service reachable even when individual servers go down.

2. A user adds items to a cart, then their next request lands on a different backend and the cart is empty. What happened and what fixes it?

Without session persistence, the balancer sent the follow-up request to a server that doesn't hold that user's session state. Sticky sessions (session affinity) pin the user to the same backend so their state survives.

3. What does a health check do, and why is failover useless without one?

It periodically tests each backend. Failover depends on the balancer knowing a server is down — without a health check it would keep routing requests to a dead backend, so users would still see failures.

4. You added a load balancer for resilience. What new risk did you introduce, and how do you address it?

The balancer itself becomes a single point of failure at the front door. Deploy it as a redundant pair (active/passive or active/active) and harden it, so the thing providing availability doesn't become the thing that takes everything down.
