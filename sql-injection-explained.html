Every SQL injection is the same mistake: the application glues what a user typed into a query string, so the database can't tell the developer's SQL apart from the attacker's. Type into the fields below and watch the query rewrite itself in real time.

01The injection lab

Four attack styles the CISSP exam expects you to recognize. Edit the input or click a payload — the SQL the database actually receives, and what it returns, update live. The amber span is the part the attacker controls.

login.php — user authentication
Payloads to try:
the query the database receives

            

          

        


        

          
1The parameter someone inputs
The username field. The password can be left blank — the attack never touches it.

          
2What the query looks for
A row whose username and password both match. The app treats "one row came back" as proof of a valid login.

          
3Why it's a risk
The closing ' ends the string early, OR '1'='1' is always true, and -- comments out the password check. The DB can't separate data from code.

          
4What happens
The WHERE clause is true for every row, so the query returns the whole users table. Login code accepts the first row — usually the admin.

        

      


      
      

        

          
 store.php?id= — product lookup

          

            
            

              
            

            

              Payloads to try:
              
              
              
            


            
the query the database receives

            

            

          

        


        

          
1The parameter someone inputs
The id in the URL, e.g. store.php?id=42. It's numeric, so it's often not even quoted — developers assume numbers are safe.

          
2What the query looks for
The three columns for product 42: name, description, price — rendered straight into the product page template.

          
3Why it's a risk
UNION staples a second query's rows onto the first. Match the column count (found with ORDER BY) and the DB runs both as one result set.

          
4What happens
Usernames and password hashes are rendered as if they were products. This is how bulk credential dumps happen — no malware, just a text field.

        

      


      
      

        

          
 check.php?id= — no data shown on the page

          

            
            

              
            

            

              Payloads to try:
              
              
              
              
            


            
the query the database receives

            

            

          

        


        

          
1The parameter someone inputs
The id, extended with a true/false test the attacker controls — a character guess, or a timed sleep.

          
2What the query looks for
Nothing useful is shown. The app only reveals whether the row matched (page A) or not (page B) — or how long the response took.

          
3Why it's a risk
The attacker infers data one bit at a time. AND '1'='1 ⇒ true page; AND '1'='2 ⇒ false page. The difference is the leak.

          
4What happens
Scripted, the yes/no oracle spells out passwords character by character. Time-based works even when both pages look identical — a 5-second delay means "true."

Later, a different feature (say "change password") reads that stored name and builds a new query with it — this time by concatenation.

Developers trust data already in their own database. The payload was dormant; the second, unsafe query is where it fires.

The stored '-- comments out the WHERE clause of the update, so the password reset applies to every account. Escaping only on input isn't enough.

        

      

    


    
    

      
02The fix is structural, not a filter

      
Blocklisting quotes and the word UNION is a losing game — encodings, comments, and case tricks slip through. The real fix changes how the query is sent: structure first, data separately.


      

        

          
✕ Vulnerable — string concatenation

          
SELECT * FROM users
WHERE username = '" + input + "';

          
The input becomes part of the command string. The database parses attacker text as SQL.

        

        

          
✓ Safe — parameterized query

          
SELECT * FROM users
WHERE username = ?;
// input bound separately as a value
stmt.setString(1, input);

          
The SQL structure is compiled first; input arrives as a pure value. ' OR '1'='1 becomes a username that matches nobody.

        

      


      

        Defense in depth, in order of leverage: parameterized queries / prepared statements (the fix) → ORM or stored procedures that parameterize under the hood → least-privilege DB accounts (the web app can't DROP or read other schemas) → input validation and allow-lists → a WAF as a backstop, never the primary control. Escaping input by hand is last-resort and error-prone — and, as second-order shows, escaping at input time alone doesn't hold.
