📋 Overview

Two classic 'implement secure protocols and services' tasks.

First, a content-filtering proxy (SquidGuard): web requests route through it and get allowed or blocked by policy, with the browser pointed at the proxy. Second, and the heart of the lab, enabling HTTPS: you generate a private key and certificate with OpenSSL, configure Apache to use them, and turn an HTTP site into an HTTPS one. Doing the certificate steps by hand demystifies the padlock you set up in Lab 21's PKI work.

[THE ONE IDEA] HTTPS is just HTTP wrapped in TLS, and TLS needs a key and a certificate. Generating them yourself shows what the certificate actually is — a public key plus identity, signed by someone — and why a self-signed one works but browsers don't trust it.

⚠️ Where students get stuck

The config traps.

[nginx vs Apache ON 80] Stop nginx before using Apache — both want the port. The lab explicitly switches services.
[PASSPHRASE ON THE KEY] A -des3 key is passphrase-protected, so Apache would prompt on every restart. The openssl rsa step removes it for unattended startup — skip it and the service hangs waiting for input.
[SELF-SIGNED WARNING] The browser warning is expected — no trusted CA signed this cert. It proves the encryption works; it doesn't mean something broke.
[CSR FIELDS] req -new asks for identity fields (Common Name especially). A mismatched CN is what causes name-mismatch errors later.
[PATHS IN SSL CONFIG] Apache's SSL config must point at the exact key and cert paths you created. A wrong path means Apache fails to start or serves the wrong cert.

🛡️ The defender's view

The lesson is 'use secure protocols' — and do the certificates properly.

Secure protocols by default

Breaks: plaintext services

HTTPS over HTTP, SSH over Telnet, SFTP over FTP. Encrypting services in transit is the baseline this lab implements.

CA-signed certs in production

Breaks: self-signed warnings

Self-signed works but isn't trusted. Real services use certs from a trusted CA (public or your enterprise PKI from Lab 21) so clients trust them without warnings.

Forward/content-filtering proxy

Breaks: unrestricted browsing

A proxy enforces web-use policy, filters malicious/forbidden sites, logs access, and hides internal clients — a control point for outbound web traffic.

Strong TLS configuration

Breaks: weak ciphers/protocols

Enabling SSL isn't enough — disable old protocols (SSLv3, TLS 1.0) and weak ciphers, and prefer modern suites. The module name is 'secure protocols,' emphasis on secure.

Protect the private key

Breaks: key theft = impersonation

The server.key is the identity. Restrict its permissions; anyone who copies it can impersonate the site. (That's why we don't email keys around.)

Certificate lifecycle

Breaks: expiry outages

A 365-day cert expires. Track and renew before it does, or the service that was 'secured' goes down — the same lifecycle discipline as full PKI.

⚡ Cheat sheet

Filter it, then encrypt it.

Commands

  • openssl genrsa -des3 -out server.key 2048
  • openssl req -new -key server.key -out server.csr
  • openssl x509 -req -days 365 -in server.csr -signkey server.key -out server.crt
  • openssl rsa -in server.key -out server.key.nopass
  • a2enmod ssl → restart apache2

Do it right

  • Secure protocols by default (HTTPS/SSH/SFTP)
  • CA-signed certs in production
  • Proxy for filtering + logging
  • Disable weak TLS protocols/ciphers
  • Protect the private key; renew before expiry

Know the terms

  • CSR — request: public key + identity
  • Self-signed — signed by its own key (untrusted)
  • a2enmod — enable an Apache module
  • Proxy — intermediary that filters/logs web traffic

✅ Check yourself

1. Walk the OpenSSL flow: what do genrsa, req, and x509 -signkey each produce?

genrsa creates the private key; req -new creates a CSR containing the public key and identity fields; x509 -req -signkey signs that CSR with its own key to produce a self-signed certificate. Together they're a complete key pair + cert made without an external CA.

2. Why does the browser warn on the finished HTTPS site, and is anything actually wrong?

The certificate is self-signed — no trusted certificate authority vouches for it — so the browser can't verify the server's identity and warns. The encryption itself works fine; in production you'd use a CA-signed certificate so clients trust it without warnings.

3. Why is the passphrase stripped from the key with openssl rsa, and what's the trade-off?

So Apache can start and restart without a human typing the passphrase each time. The trade-off is that a passphrase-free key file is more dangerous if stolen — anyone who copies it can use it — so it must be tightly protected by file permissions.

4. A proxy is called a security control here, not just a performance one. Name two security functions it provides.

It filters/blocks malicious or policy-violating sites and logs web access (useful for monitoring and investigations). It also hides internal client details from external servers. Any two of filtering, logging, and client anonymization.
