📋 Overview

The other side of every other lab in this series.

A NIDS (network IDS, like the Suricata/Zeek sensors in Security Onion) watches traffic on the wire; a HIDS watches what happens on a single host. In this lab you play both attacker and analyst: run an nmap scan to create suspicious traffic, capture it, import the pcap into Security Onion with so-import-pcap, then move into the analyst role — reading the alerts it fires, escalating the genuine one to a case, adding observables and tasks, and closing it. That workflow is the lesson.

[THE ONE IDEA] An alert is not an incident. The skill is triage — separating the one alert that matters from the noise, then building the case that proves it.

🧭 The walkthrough

Make the noise, capture it, feed the sensor, work the case.

Phase 1 · Generate & capture

Create something worth alerting on

kali@kali$ wireshark & # start a capture kali@kali$ nmap -T4 -A -v 172.16.1.10 # aggressive, obvious scan kali@kali$ nmap -T5 203.0.113.1 192.168.0.0/24 172.16.1.0/28

An -T4 -A scan is deliberately loud — version detection, OS detection, scripts — exactly the kind of traffic a NIDS is tuned to catch. Capture it in Wireshark and save the pcap.

Phase 2 · Import into Security Onion

Let the sensor analyze the capture

sysadmin@seconion:~$ sudo so-status # confirm all modules OK sysadmin@seconion:~$ sudo so-import-pcap ~/Downloads/scan.pcap

so-import-pcap replays the capture through Security Onion's detection stack so its rules fire as if the traffic were live. Check so-status first — if a module is down, alerts won't generate.

📸Screenshot for your report: so-import-pcap completing, and so-status showing modules OK.
Phase 3 · Triage the alerts

Read what fired

In the Security Onion interface (Alerts / Hunt), find the suspicious inbound activity and the nmap scan alert. Read each one: source, destination, rule name, severity. Most traffic is benign — the job is to pick out the alert that represents a real attack and set the rest aside.

📸Screenshot for your report: the alerts list with the nmap-scan alert identified.
Phase 4 · Work the case

Escalate, investigate, close

Escalate the real alert to a case. Add observables (the attacker IP, the targeted hosts/ports) and tasks (what to check, who to notify). Investigate using the linked data, complete the tasks, then close the case with a disposition. This is the documented, repeatable process a SOC runs on every real alert — and the audit trail an investigation depends on.

⚠️ Where students get stuck

What goes wrong here.

[MODULES DOWN] If so-status doesn't report everything OK, imported traffic won't generate alerts. Wait for the stack to come up (it can be slow after a boot) before importing.
[FIREWALL STEP] The lab has you disable a firewall rule so the scan traffic reaches the sensor's view. That's a pod setup step — note it, and that it's not something you'd do in production.
[PCAP PATH] so-import-pcap needs the exact path to your saved capture (e.g. ~/Downloads/scan.pcap). A wrong path silently does nothing useful.
[ALERT ≠ INCIDENT] Don't escalate everything. Most alerts are noise or benign; the exercise is choosing the one that warrants a case and justifying why.
[CLOSING WITHOUT A TRAIL] A case closed with no observables, tasks, or disposition teaches nothing. The documentation is the deliverable — fill it in.

🛡️ The defender's view

Here the whole lab is the defense. These are the pieces that make it work.

NIDS (network sensor)

Breaks: wire-level attacks

Suricata/Zeek inspect traffic for known-bad patterns — scans, exploits, C2. It's the tripwire that fired on the nmap scan.

HIDS / endpoint telemetry

Breaks: on-host activity

Host agents catch what never crosses the wire — file changes, process spawns, privilege use. NIDS and HIDS cover each other's blind spots.

Alert tuning

Breaks: analyst fatigue

Too many false positives and the real alert drowns. Tuning rules and suppressing known-benign noise is what makes triage possible.

Case management / documentation

Breaks: losing the thread

Observables, tasks, and dispositions turn a fleeting alert into a repeatable, auditable investigation — and evidence if it becomes an incident.

SIEM correlation

Breaks: single-signal blindness

Correlating NIDS, HIDS, and logs connects an alert to the activity around it, so one scan becomes a story rather than an isolated ping.

The analyst workflow

Breaks: everything

Detect → triage → escalate → investigate → close is the control. Tools generate signals; the process turns signals into decisions.

✅ Check yourself

1. What's the difference between a NIDS and a HIDS, and why run both?

A NIDS inspects network traffic for malicious patterns; a HIDS watches activity on an individual host (files, processes, logins). Each sees what the other can't — an on-wire scan vs. an on-host privilege change — so together they close each other's blind spots.

2. Security Onion fires 200 alerts from one scan. Is that an incident? What do you do?

Not by itself — an alert is a signal, not a confirmed incident. You triage: identify the alerts that represent real malicious activity, set aside the noise, and escalate only the genuine one to a case for investigation.

3. Why does a case need observables and tasks rather than just being marked 'closed'?

Observables (attacker IP, targeted ports) and tasks create a documented, repeatable investigation and an audit trail. If the event becomes an incident or goes to legal/IR, that record is the evidence and the basis for a defensible disposition.

4. Which part of this lab is the actual security control?

The analyst workflow — detect, triage, escalate, investigate, close. The tools produce signals, but the repeatable process that turns signals into documented decisions is what defends the organization.
