Configuring a RADIUS Server

Instead of every switch, VPN, and access point checking passwords on its own, they all ask one server. That server is RADIUS, and this lab builds it two ways — Windows NPS and FreeRADIUS — then proves it with a test authentication.

⏱ ~60 min 📶 Difficulty: Intermediate 🧰 Tools: Windows NPS · FreeRADIUS · radtest 🎯 Build: a central AAA server 📘 Maps to: Module 10 — Identity, Automation, Incident Response, and Forensics
[AUTHORIZED TESTING ONLY] This lab stands up an authentication server inside an isolated pod. A RADIUS server is a central identity control; a weak shared secret or exposed configuration can undermine authentication for everything that relies on it.

📋 Overview

One place to say yes or no to access.

RADIUS centralizes AAA — Authentication (who are you), Authorization (what may you do), and Accounting (what did you do). Network devices (a VPN, a wireless controller, a switch doing 802.1X) become RADIUS clients that forward credentials to the server for a verdict, so identity lives in one audited place instead of scattered across every device. You'll configure it on Windows (Network Policy Server) and on Ubuntu (FreeRADIUS), then test with radtest.

[THE ONE IDEA] RADIUS turns 'every device manages its own logins' into 'every device asks one server.' That centralization is the control — consistent policy, central logging, one place to disable an account.

🧭 The walkthrough

Two implementations, one test.

Phase 1 · Windows NPS

RADIUS the Microsoft way

Add the Network Policy and Access Services role (Network Policy Server), then configure a network policy: the conditions a request must meet, the RADIUS clients allowed to ask, and the shared secret that authenticates those clients to the server. NPS is how Windows environments centralize network authentication.

📸Screenshot for your report: the NPS role installed and a network policy configured.
Phase 2 · FreeRADIUS

RADIUS the open-source way

sysadmin@ubuntusrv:~$ sudo nano /etc/freeradius/3.0/mods-config/files/authorize # add a test user sysadmin@ubuntusrv:~$ sudo freeradius -X # run in debug mode — shows every decision

Add a user to the authorize file, then run FreeRADIUS with -X (debug), which prints exactly what happens on each request — the single most useful troubleshooting tool here.

Phase 3 · Test it

Ask for a verdict

sysadmin@ubuntusrv:~$ radtest testing password 127.0.0.1 18120 testing123

The arguments are username, password, server, port, and the shared secret (testing123). A correct request returns Access-Accept; wrong credentials or a mismatched secret return a reject. That exchange is exactly what a switch or VPN does on every login.

📸Screenshot for your report: the radtest command returning Access-Accept.

⚠️ Where students get stuck

RADIUS-specific friction.

[SHARED SECRET MISMATCH] The secret must match on both the client and the server. A mismatch causes rejects or silence — check it first when auth fails.
[USE -X TO DEBUG] freeradius -X shows every step of a request. If authentication isn't working, the reason is almost always printed there.
[radtest ARGUMENT ORDER] It's user pass server port secret. Get the order (or the port/secret) wrong and you'll get a reject that looks like a credential problem.
[AUTHORIZE FILE SYNTAX] The FreeRADIUS user entry has a specific format. A small syntax slip means the user is never matched.
[NPS CONDITIONS] On Windows, the network policy's conditions must actually match the request, or NPS denies it even with correct credentials.

🛡️ The defender's view

Centralized identity is the control — here's how to run it safely.

Centralized AAA

Breaks: scattered, inconsistent logins

One server for authentication, authorization, and accounting means consistent policy, central logging, and one place to disable a compromised account instantly.

Protect the shared secret

Breaks: client impersonation

The secret authenticates each device to the server. Make it long and unique per client, and guard it — a leaked secret lets an attacker pose as a trusted network device.

Pair with 802.1X / EAP

Breaks: open network ports

RADIUS behind 802.1X gives per-user network authentication (wired and WPA2/3-Enterprise Wi-Fi) instead of a single shared key — the enterprise standard, and the link to the wireless lab.

Accounting & logging

Breaks: no audit trail

The second 'A' matters: RADIUS accounting records who connected, when, and for how long — essential for monitoring and investigations.

Add MFA

Breaks: password-only auth

Front RADIUS with multi-factor so a stolen password alone can't get on the network.

Encrypt the transport (RadSec)

Breaks: weak legacy crypto

Classic RADIUS protects only the password, poorly. RADIUS over TLS (RadSec) secures the whole exchange on untrusted links.

✅ Check yourself

1. What does AAA stand for, and what does RADIUS centralize?

Authentication (who you are), Authorization (what you're allowed), and Accounting (a record of what you did). RADIUS centralizes all three on one server that network devices query, instead of each device managing logins itself.

2. What is the RADIUS shared secret for, and why protect it?

It authenticates each RADIUS client (a switch, VPN, or access point) to the server. If it leaks, an attacker can impersonate a trusted network device and interact with the authentication server, so it must be strong, unique per client, and kept secret.

3. Where does RADIUS connect to wireless security?

In WPA2/WPA3-Enterprise (802.1X), the access point is a RADIUS client that forwards each user's credentials to the RADIUS server — giving per-user authentication instead of one shared Wi-Fi passphrase.

4. FreeRADIUS auth is failing. What's the fastest way to find out why?

Run it with freeradius -X (debug mode), which prints every step of each request and decision. The cause — a bad secret, a user not matched, a config error — is almost always visible there.
