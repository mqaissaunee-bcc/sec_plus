Capturing Network Traffic

The same tools a defender uses to monitor a network let anyone on the wire read unencrypted traffic. This lab proves it: capture an FTP login and the username and password are right there in the clear — then watch SFTP hide them.

⏱ ~55 min 📶 Difficulty: Beginner→Intermediate 🧰 Tools: tcpdump · Wireshark · dumpcap · NetworkMiner 🎯 Protocols: ICMP · ARP · FTP vs SFTP · HTTP 📘 Maps to: Module 9 — Vulnerability Management, Monitoring, and Enterprise Controls
[AUTHORIZED TESTING ONLY] Capturing network traffic can expose other people's credentials and data. Sniffing traffic on networks you do not own or have written permission to monitor is illegal in most jurisdictions.

📋 Overview

One lab, one unforgettable point: encryption in transit is not optional.

You'll capture traffic three ways — tcpdump (command line), Wireshark (GUI), and dumpcap/NetworkMiner — across several protocols. The moment that lands: capture an FTP login and the username and password appear in plaintext, readable by anyone on the path. Capture the same login over SFTP and after the Diffie-Hellman key exchange everything is encrypted — the credentials are gone from view. That contrast is the whole argument for secure protocols.

[THE ONE IDEA] If it's not encrypted in transit, assume it's public. FTP, Telnet, and plain HTTP hand their contents to anyone on the wire; SFTP, SSH, and HTTPS don't.

🧭 The walkthrough

Capture, read, and compare cleartext against encrypted.

Phase 1 · tcpdump basics

Capture from the command line

kali@kali$ ping 192.168.0.50 sysadmin@seconion:~$ sudo tcpdump -i ens192 icmp # only ICMP sysadmin@seconion:~$ sudo tcpdump -i ens192 arp # only ARP sysadmin@seconion:~$ sudo tcpdump -i ens192 -w cap.pcap # save to a file

A capture filter like icmp or arp limits what's recorded to one protocol. The output line reads time IP src > dst: type, id, seq, len. -w writes a pcap instead of printing — that's how an admin saves evidence for later analysis; Ctrl+C stops the capture.

📸Screenshot for your report: tcpdump output filtered to ICMP (and the saved .pcap).
Phase 2 · FTP in the clear

The point of the whole lab

kali@kali:~$ ftp 192.168.0.50 # log in as anonymous / anonymous

Capture this login in Wireshark and follow the stream: the USER and PASS commands show the username and password as readable text. FTP sends credentials with no protection at all — anyone capturing the link has them.

📸Screenshot for your report: Wireshark showing the FTP username and password in plaintext.
Phase 3 · SFTP encrypted

The same login, hidden

kali@kali:~$ sftp sysadmin@192.168.0.6

Capture the SFTP session and you'll see the Diffie-Hellman key exchange up front — and after it, nothing readable. The login and file transfer are encrypted over the medium. Same task, same credentials, completely different exposure.

📸Screenshot for your report: the Wireshark SFTP capture: the key exchange, then encrypted (unreadable) packets.
Phase 4 · HTTP with dumpcap & NetworkMiner

Reassemble what crossed the wire

sysadmin@seconion:~$ sudo dumpcap -P -i ens192 -w /tmp/netcapture2.pcap sysadmin@seconion:~$ sudo networkminer # carve files/creds from the capture

dumpcap is Wireshark's lightweight capture engine, good for long or headless captures. NetworkMiner reassembles a capture into the files, images, and credentials that passed by — making the cost of plain HTTP vivid.

⚠️ Where students get stuck

The small things that derail a capture.

[WRONG INTERFACE] Capture on the interface the traffic actually uses (e.g. ens192) — confirm with ifconfig -a / netstat -i. The wrong NIC captures nothing.
[CAPTURE vs DISPLAY FILTER] tcpdump's icmp/arp are capture filters (what's recorded); Wireshark's filter box is usually a display filter (what's shown). Different syntax, different stage.
[NEED ROOT] Capturing requires privilege — run tcpdump/dumpcap with sudo or you'll get a permissions error.
[EXPECTING TO READ SFTP] You can't — that's the lesson. After the key exchange the payload is encrypted. Seeing gibberish means it's working.
[FOLLOW THE STREAM] In Wireshark, right-click an FTP packet → Follow → TCP Stream to read the whole conversation, rather than hunting packet by packet.

🛡️ The defender's view

The fix is almost entirely 'encrypt it,' plus using these same tools defensively.

Secure protocols

Breaks: the plaintext exposure

Replace FTP/Telnet/HTTP with SFTP/FTPS, SSH, and HTTPS. Encryption in transit is the direct answer to a sniffer reading credentials.

Encryption everywhere (TLS)

Breaks: on-path reading

TLS makes captured traffic useless to an eavesdropper. If a protocol has a secure variant, use it; if it doesn't, tunnel it.

Network monitoring (defensive capture)

Breaks: blind spots

These same tools — tcpdump, Wireshark, SIEM taps — are how defenders detect anomalies. Capture is a control when it's yours.

Switched networks + port security

Breaks: passive sniffing

Switches limit which traffic reaches a given port; disabling SPAN/mirror access and locking ports makes casual sniffing harder.

Network segmentation

Breaks: exposure radius

Segmentation limits what any one captured link can reveal — a sniffer on one VLAN can't see another.

Credential hygiene

Breaks: the payoff

Assume transit can be observed: don't reuse passwords, prefer keys/MFA, and rotate anything that ever traveled in the clear.

Capture it, and the lesson it teaches.

  • Wireshark: Follow → TCP Stream
  • dumpcap -P -i IF -w file.pcap
  • NetworkMiner reassembles files/creds

The lesson & fix

  • FTP/Telnet/HTTP = plaintext creds
  • SFTP/SSH/HTTPS = encrypted
  • Use secure protocols everywhere
  • Segment + switch port security
  • Rotate anything sent in the clear

Know the terms

  • pcap — a saved packet capture
  • Capture vs display filter — record vs show
  • Cleartext — unencrypted, readable
  • Key exchange — the start of encryption (DH)

✅ Check yourself

1. You capture an FTP login and an SFTP login. What's different in the two captures, and why?

The FTP capture shows the username and password in plaintext — FTP sends credentials unencrypted. The SFTP capture shows a Diffie-Hellman key exchange followed by encrypted, unreadable packets. SFTP protects the session; FTP does not.

2. What's the single most important fix for the exposure this lab demonstrates?

Use secure, encrypted protocols in transit — SFTP/FTPS instead of FTP, SSH instead of Telnet, HTTPS instead of HTTP. Encryption makes a captured stream useless to an eavesdropper.

3. tcpdump and Wireshark are hacking tools in this lab. How are they also defensive controls?

They're the standard tools for network monitoring and investigation. Defenders use the same captures to detect anomalies, investigate incidents, and verify that traffic is actually encrypted. The tool is neutral; authorization and intent decide which it is.

4. A protocol you must use has no encrypted version. What are your options?

Tunnel it inside something encrypted (VPN, SSH tunnel, TLS wrapper) so the cleartext never crosses an observable medium, and segment/restrict the network path so fewer parties can capture it.
