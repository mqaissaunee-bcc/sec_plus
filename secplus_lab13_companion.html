IoT Management

📋 Overview

The security problem with IoT is scale and weakness at once.

IoT and embedded devices are everywhere, often shipped with weak defaults, rarely patched, and built with little security. This lab puts you on the management side: run ThingsBoard (an IoT platform) in Docker, create accounts with different roles (tenant, customer), register a device, and send it telemetry over MQTT with mosquitto_pub. Managing devices centrally — identity, roles, monitoring — is how you bring order to a fleet that would otherwise be hundreds of unmanaged endpoints.

[THE ONE IDEA] You can't harden a thousand devices one at a time. The control is central management plus segmentation — know every device, scope its access, watch its traffic, and keep it off the networks that matter.

🧭 The walkthrough

Stand up the platform, scope the accounts, connect a device.

Phase 1 · Start the platform

ThingsBoard in a container

sysadmin@ubuntusrv:~$ sudo docker run -it -p 9090:9090 -p 1883:1883 -p 7070:7070 ... thingsboard

The container exposes the web UI (9090) and the MQTT broker (1883) — MQTT being the lightweight publish/subscribe protocol most IoT devices speak. Those exposed ports are also the attack surface: a management UI and a broker reachable on the network.

Phase 2 · Create scoped accounts

Roles, not one god-account

ThingsBoard separates tenant (manages devices and rules) from customer (sees only their own devices). Creating these is role-based access control in miniature: each account gets only what it needs, so a compromised customer login can't touch the whole fleet.

📸Screenshot for your report: the tenant and customer accounts created with their roles.
Phase 3 · Add a device & send data

Register, then report telemetry

sysadmin@ubuntusrv:~$ mosquitto_pub -d -q 1 -h 127.0.0.1 -t v1/devices/me/telemetry -u <TOKEN> -m '{"temp":22}'

Add a device in the platform (which issues it an access token), add a rule chain to process its data, then publish telemetry to the broker as that device. The platform receives, stores, and displays the reading. The token is the device's identity — how the broker knows which device is talking and whether it's allowed to.

📸Screenshot for your report: the published telemetry appearing in the device's dashboard.

⚠️ Where students get stuck

The usual friction.

[CONTAINER STILL STARTING] ThingsBoard takes a while to initialize. Hitting the web UI too early shows errors — wait for the service to finish coming up.
[DEVICE TOKEN] The publish must use the device's access token. Wrong or missing token and the broker rejects the message — that rejection is authentication working.
[MQTT TOPIC] Telemetry goes to a specific topic (e.g. v1/devices/me/telemetry). Publish to the wrong topic and the data never reaches the dashboard.
[ROLE CONFUSION] Tenant vs customer scopes see different things. If a device seems missing, check you're logged in as the role that owns it.
[PLAINTEXT MQTT] This lab uses MQTT without TLS for simplicity. Note that — unencrypted MQTT exposes telemetry and tokens, which is a real-world weakness, not a feature.

🛡️ The defender's view

IoT security is mostly about containing devices you can't fully trust.

Network segmentation

Breaks: a compromised device pivoting

Put IoT on its own VLAN/segment away from critical systems. If a weak device is owned, it can't reach what matters. The single most important IoT control.

Change default credentials

Breaks: trivial takeover

Default usernames/passwords are the #1 IoT attack vector (think Mirai). Change them and enforce per-device identity like the platform's tokens.

Firmware updates

Breaks: unpatched known flaws

Embedded devices rarely auto-update. A management platform that tracks and pushes firmware closes known vulnerabilities before they're exploited.

Central management + inventory

Breaks: unmanaged sprawl

You can only secure what you know exists. A platform gives you inventory, identity, and monitoring across the whole fleet at once.

Encrypt MQTT (TLS) + authenticate

Breaks: sniffed telemetry/tokens

Plain MQTT exposes data and credentials on the wire. MQTT over TLS with per-device auth protects both — the fix for this lab's simplification.

Least-privilege roles

Breaks: one login owning everything

Tenant vs customer scoping limits blast radius. A compromised account should see only its own devices, never the entire estate.

⚡ Cheat sheet

Manage the fleet, contain the risk.

The build

  • Run ThingsBoard in Docker (ports 9090/1883)
  • Create tenant + customer accounts
  • Add device → get access token
  • Add rule chain
  • mosquitto_pub telemetry to the broker

Secure IoT

  • Segment IoT onto its own network
  • Change default credentials
  • Keep firmware updated
  • Central inventory + monitoring
  • MQTT over TLS + per-device auth

Know the terms

  • IoT / embedded — small special-purpose devices
  • MQTT — lightweight pub/sub IoT protocol
  • Telemetry — the data a device reports
  • Segmentation — isolating device networks

✅ Check yourself

1. Why is network segmentation considered the most important IoT security control?

IoT devices are often weak and unpatchable, so you assume some will be compromised. Segmenting them onto their own network means a compromised device can't reach critical systems — you contain the damage rather than trying (and failing) to make every device secure.

2. Default credentials are singled out as the top IoT risk. Why so dangerous here specifically?

IoT devices ship with well-known default usernames/passwords and are rarely changed, so attackers (and worms like Mirai) can take over huge numbers at once by trying defaults. Per-device credentials/tokens and forced changes shut that down.

3. The lab uses MQTT without TLS. What's exposed, and what's the fix?

Unencrypted MQTT exposes the telemetry and the device's access token to anyone capturing the traffic — letting an attacker read data and impersonate the device. The fix is MQTT over TLS with per-device authentication.

4. What does a central management platform give you that securing devices individually can't?

Inventory, identity, monitoring, and update management across the whole fleet at once — you can't secure what you don't know exists, and at IoT scale per-device hardening isn't feasible. Central management plus role scoping is how you bring the fleet under control.
