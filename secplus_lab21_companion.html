📋 Overview

PKI is a trust machine — this lab builds one from scratch.

Public Key Infrastructure is how we bind a public key to an identity so strangers can trust each other. At its center is a Certificate Authority (CA) that vouches for identities by signing their certificates. You'll add the Active Directory Certificate Services role to a Windows server, configure it as a CA, then install IIS and request a certificate from your own CA — the same flow that puts the padlock on a real website.

[THE ONE IDEA] Trust flows from the root. A certificate is only as trustworthy as the CA that signed it, and everything that trusts the CA inherits whatever the CA vouches for. Protecting the CA is protecting the PKI.

The asymmetric-crypto spine underneath: the server keeps a private key secret and publishes a public key inside a certificate the CA has signed. Clients verify the CA's signature, then trust the key. Encryption and identity in one structure.

🧭 The walkthrough

This lab is Windows GUI work; here's what each stage is really doing.

Phase 1 · Add the role

Install AD Certificate Services

In Server Manager → Add Roles and Features, add Active Directory Certificate Services with the Certification Authority role service. This installs the machinery; it doesn't yet make the server a working CA. Keep the role-based installation default.

📸Screenshot for your report: the AD CS role selected in the Add Roles and Features wizard.
Phase 2 · Configure the CA

Turn the role into an authority

Run the post-install configuration. The choices that matter for the exam: Enterprise vs Standalone (Enterprise integrates with AD so domain clients trust it automatically), Root vs Subordinate (a root CA signs itself and anchors the chain; a subordinate is signed by a root), the key length and hash (e.g. 2048-bit, SHA-256), and the validity period. Those settings define how strong and how trusted every certificate it issues will be.

📸Screenshot for your report: the CA configuration (root/enterprise, key length, validity).
Phase 3 · Issue a certificate

Give a web server an identity

Install IIS, then from IIS request a certificate — this generates a key pair and a certificate signing request (CSR) containing the public key and identity details. Your CA reviews and signs it, and the signed certificate is bound to the site. A browser that trusts your CA will now trust the site's certificate: the full issue-and-trust loop in miniature.

📸Screenshot for your report: the certificate issued by your CA and bound to the IIS site.

⚠️ Where students get stuck

The conceptual forks that confuse people here.

[ROLE ≠ CONFIGURED CA] Adding the role doesn't create a CA. You must run the post-deployment configuration afterward — skipping it leaves a CA that can't issue anything.
[ENTERPRISE vs STANDALONE] Enterprise CAs integrate with Active Directory (auto-enrollment, auto-trust for domain members); Standalone don't. The lab's choice determines whether clients trust certs automatically.
[ROOT vs SUBORDINATE] A root CA signs its own certificate and anchors trust; a subordinate is signed by a parent. Mixing these up breaks the chain-of-trust mental model the exam tests.
[CSR DIRECTION] The server generates the key pair and sends a request (public key + identity); the CA signs it. The private key never leaves the server — that's the whole point.
[TRUST THE CA, NOT THE CERT] A browser warning means the client doesn't trust your CA, not that the certificate is 'bad.' Trust is established by distributing the CA's root certificate.

🛡️ The defender's view

A CA is the crown jewels — most of PKI defense is protecting and governing it.

Protect the CA private key

Breaks: total compromise

Whoever holds the CA key can forge trust for anything. Keep root keys offline/HSM-backed with strict access — a stolen CA key breaks the entire PKI.

Offline root + subordinate CAs

Breaks: single point of failure

Keep the root CA offline and issue day-to-day certs from subordinate (issuing) CAs. A compromised issuing CA can be revoked without rebuilding trust.

Revocation (CRL / OCSP)

Breaks: compromised or stale certs

A cert can't always wait to expire. Publish revocation via CRL/OCSP so clients can reject keys that were lost, misissued, or superseded.

Short validity + rotation

Breaks: long-lived exposure

Shorter certificate lifetimes limit the damage window if a key leaks and force regular re-validation of identity.

Certificate lifecycle management

Breaks: sprawl & expiry outages

Track issuance, renewal, and expiry. Expired certs cause outages; untracked certs become blind spots. Automate enrollment and renewal.

Strong parameters

Breaks: weak crypto

2048-bit+ keys and SHA-256+ signatures. Weak keys or deprecated hashes undermine every certificate the CA signs.

⚡ Cheat sheet

The PKI pieces and how they fit.

The build

  • Add role: AD Certificate Services
  • Configure CA (root/enterprise, 2048/SHA-256)
  • Install IIS
  • Request cert (generates key pair + CSR)
  • CA signs → bind to site

Protect the PKI

  • Guard the CA private key (offline/HSM)
  • Offline root + issuing subordinates
  • Revocation: CRL / OCSP
  • Short validity + rotation
  • Lifecycle management (no surprise expiry)

Know the terms

  • CA — signs/vouches for certificates
  • CSR — request: public key + identity
  • Root vs subordinate — anchor vs delegated
  • CRL / OCSP — revocation mechanisms
  • Chain of trust — cert → issuer → root

✅ Check yourself

1. In one sentence, what problem does a CA solve?

It binds a public key to a verified identity and vouches for that binding with its signature, so parties who don't know each other can establish trust through a third party they both trust.

2. The server generates its own key pair and sends a CSR to the CA. Why does the private key never go to the CA?

The private key is the server's secret — sending it would defeat asymmetric cryptography. The CSR contains only the public key and identity; the CA signs that, and the server proves ownership by holding the matching private key.

3. Why keep a root CA offline and issue certificates from subordinate CAs?

The root is the anchor of all trust; if its key is compromised, the entire PKI must be rebuilt. Keeping it offline and delegating day-to-day issuance to subordinate CAs means a compromised issuing CA can be revoked and replaced without destroying the root of trust.

4. A certificate is valid for another year, but the private key was leaked today. What do you do, and what mechanism makes it work?

Revoke the certificate immediately rather than waiting for expiry, and publish the revocation so clients stop trusting it — via a Certificate Revocation List (CRL) or OCSP, which clients check before accepting a certificate.
