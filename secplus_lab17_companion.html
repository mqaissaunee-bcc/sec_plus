Configuring a Network-Based Firewall

A firewall is where network security policy becomes real rules. This lab works a pfSense firewall through three jobs — block a protocol, redirect traffic to an internal host, and stand up a VPN for secure remote access — the everyday work of controlling a perimeter.

⏱ ~70 min 📶 Difficulty: Intermediate 🧰 Tools: pfSense · OpenVPN 🎯 Do: block, forward, and VPN 📘 Maps to: Module 6 — Architecture Models and Enterprise Infrastructure
[AUTHORIZED TESTING ONLY] This lab reconfigures a firewall inside an isolated pod. Firewall and VPN changes directly control what can reach a network — a wrong rule can expose or isolate real systems, so understand each rule before applying it anywhere live.

📋 Overview

Three firewall jobs that cover most of what a perimeter does.

You'll drive a pfSense firewall through three tasks: block ICMP (a simple allow/deny rule, verified by a ping that stops working), port forwarding (NAT a port from the outside to an internal host, retargeting an SSH connection), and a VPN (stand up an OpenVPN server, export a client config, connect, and manage the session). Together they're the core of controlling and securing a network boundary.

[THE ONE IDEA] A firewall enforces policy through rules evaluated in order, ideally on a default-deny base: block everything, then allow only what's needed. Every rule you add is a deliberate exception to 'no.'

🧭 The walkthrough

Block, redirect, tunnel.

Phase 1 · Block a protocol

Deny ICMP and prove it

kali@kali$ ping -c4 172.16.1.10 # works before the rule... kali@kali$ ping -c4 172.16.1.10 # ...times out after the block rule is applied

Add a pfSense rule to block ICMP, then ping the target — the ping now fails. This is the simplest possible demonstration of a firewall rule: a specific protocol, denied, with observable effect. (It's also why hosts behind firewalls look 'down' to nmap — Lab 07's lesson, from the defender's side.)

📸Screenshot for your report: the ping succeeding, then failing after the block-ICMP rule is applied.
Phase 2 · Port forwarding (NAT)

Send an outside port to an inside host

kali@kali$ ssh sysadmin@203.0.113.1 # hitting the firewall's WAN address...

Configure a NAT port-forward so a connection to the firewall's external address is redirected to an internal host. Now an SSH to the firewall's WAN IP lands on the internal server. Port forwarding is how services behind NAT become reachable — useful and, done carelessly, a way to expose internal hosts.

📸Screenshot for your report: the SSH connection to the firewall's WAN address reaching the internal host.
Phase 3 · VPN for remote access

An encrypted tunnel in

kali@kali$ cd ~/Downloads kali@kali$ unzip pfSense-UDP4-1194-vpnuser-config.zip

Set up an OpenVPN server on pfSense, export the client config, import it on Kali, and connect. The VPN gives a remote user an encrypted tunnel into the network — the right way to provide remote access, versus exposing individual services. Then manage the active connection from the firewall.

📸Screenshot for your report: the VPN client connected and the session shown in pfSense.

⚠️ Where students get stuck

Firewall-specific gotchas.

[RULE ORDER] pfSense evaluates rules top-down and stops at the first match. A block below an allow (or vice-versa) may never fire — order matters as much as the rules themselves.
[APPLY CHANGES] Edits don't take effect until you click Apply. A 'rule that isn't working' is often a rule that was never applied.
[WAN vs LAN INTERFACE] Rules are per-interface. A rule on the wrong interface silently does nothing — inbound internet rules go on WAN.
[NAT + FIREWALL RULE] A port-forward usually needs both the NAT mapping and an associated firewall rule to permit the traffic. One without the other fails.
[VPN CONFIG MATCH] The exported client config must match the server (protocol, port 1194, certs). A mismatch means the client never connects.

🛡️ The defender's view

This lab is pure blue team — the design principles behind the rules.

Default-deny

Breaks: implicit exposure

Start by blocking everything, then allow only required traffic. A default-allow firewall exposes anything you forgot to block; default-deny exposes only what you chose to permit.

Least-privilege rules

Breaks: over-broad allows

Each rule should be as specific as possible — source, destination, port. Broad 'any-any' rules defeat the point of having a firewall.

VPN for remote access

Breaks: exposed internal services

A VPN gives remote users an encrypted, authenticated tunnel instead of port-forwarding each service to the internet — far less attack surface.

Careful NAT / port-forwarding

Breaks: accidental exposure

Every forward is a hole through the perimeter to an internal host. Forward only what must be reachable, to hardened targets, and know exactly what you've exposed.

Logging & monitoring

Breaks: blind perimeter

Firewall logs show what's being blocked and allowed — feed them to a SIEM. A firewall you don't watch can't tell you you're under attack.

Segmentation

Breaks: flat networks

Firewalls between internal zones (not just at the edge) contain lateral movement — secure network design is layers of control, not one wall.

✅ Check yourself

1. What does 'default-deny' mean and why is it the safer base for a firewall?

Block all traffic by default and add explicit rules only for what's needed. It's safer because anything you forget is denied rather than allowed — a default-allow firewall exposes every service you didn't remember to block.

2. pfSense evaluates rules top-down, first match wins. Why does that make rule order critical?

Because evaluation stops at the first matching rule. An allow placed above a block (or vice-versa) means the lower rule never fires — so two correct-looking rules in the wrong order produce the wrong behavior.

3. Why is a VPN preferable to port-forwarding several internal services to the internet?

A VPN provides one encrypted, authenticated entry point and puts remote users 'inside' the network, instead of exposing each service directly. Port-forwarding multiple services multiplies the internet-facing attack surface; the VPN minimizes it.

4. Port forwarding is useful but risky. What's the risk and how do you limit it?

Every forward punches a hole through the perimeter to an internal host, which can expose that host to the internet. Limit it by forwarding only truly necessary ports, to hardened/patched targets, restricting allowed sources, and logging the traffic.
